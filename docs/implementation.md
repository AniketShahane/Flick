# Flick — implementation reference

This document describes the implemented v2 pair-to-play path. The binding schemas and timing rules are in [control-channel.md](design/control-channel.md), with executable reference bytes in [control-v2-fixtures.md](design/control-v2-fixtures.md). Direct-play remains the product invariant: Flick never transcodes or screen-mirrors.

### Build types, R8, and baseline profiles

Both apps declare three authored build types plus two synthesized by the baseline-profile
plugin.

| Type | `isMinifyEnabled` | `isDebuggable` | Signing | Role |
| --- | --- | --- | --- | --- |
| `debug` | false | true | debug | development; interpreted/JIT, no profile |
| `release` | **true** (+ `isShrinkResources`) | false | debug keystore | shipped shape; packages the baseline profile |
| `benchmark` | false | false | debug keystore | macrobenchmark target: AOT-compiled but symbol-readable |
| `nonMinifiedRelease` | false | false | debug keystore | plugin-synthesized profile-capture target |
| `benchmarkRelease` | inherits `release` | false | debug keystore | plugin-synthesized comparison target |

The `release` signing config points at the **debug** keystore. That is a local-testing
identity so a release APK can be installed for performance measurement; it is not a
distribution identity, and no keystore file, password, or credential is stored in the
repository.

Everything the project previously exercised was a debug build, which ART never compiles
ahead of time. Both apps now depend on `androidx.profileinstaller` so a packaged profile is
actually handed to ART on first run, and `:baselineprofile:sender` / `:baselineprofile:receiver`
(`com.android.test` modules on `androidx.benchmark:benchmark-macro-junit4`) generate those
profiles. One test module can name exactly one `targetProjectPath`, which is why there are
two of them.

Declaring those plugins costs one online build. Gradle resolves a plugin marker and the
whole classpath behind it at configuration time even under `apply false`, so the
`androidx.baselineprofile` and `com.android.test` chains are fetched before any task is
selected — a cold cache therefore fails `:sender:assembleDebug` as surely as it fails a
profile run. The configuration-time set is
`androidx.baselineprofile:androidx.baselineprofile.gradle.plugin:1.5.0-alpha07`,
`androidx.benchmark:benchmark-baseline-profile-gradle-plugin:1.5.0-alpha07`,
`com.google.testing.platform:core-proto:0.0.8-alpha08` and
`com.android.test:com.android.test.gradle.plugin:9.3.0`; the marker's own
`com.android.tools.build:gradle:9.3.0` is already present because the application plugin
pulls it. Compiling `:baselineprofile:*` additionally needs `benchmark-macro-junit4`,
`benchmark-macro`, `benchmark-common` and `benchmark-traceprocessor` at `1.5.0-alpha07`,
`androidx.test.uiautomator:uiautomator:2.4.0`, `androidx.test:rules:1.5.0`, and
`com.squareup.wire:wire-runtime:6.4.0` — the one coordinate here that comes from Maven
Central rather than Google's Maven. All of it is current and resolvable; nothing is
yanked. After the first successful resolve the build is `--offline`-clean again.

The generators exercise the journeys that dominate first-run cost: on the phone, cold start,
the library grid fling, the film detail sheet, the Now Playing remote, and the metrics and
subtitles sheets; on the TV, cold start, the idle/pair focus graph, Settings, playback chrome
show/hide, and the subtitles and metrics panels. Every interaction is best-effort — the TV's
playback routes only exist while a phone is casting, and a generator run cannot arrange that,
so those steps are attempted and skipped silently rather than failing the run.

Generation is off the assemble path (`automaticGenerationDuringBuild = false`), so
`assembleDebug` and `assembleRelease` never require a connected device; they package whatever
profile is committed under `src/release/generated/baselineProfiles/`. Refreshing a profile is
an explicit, device-attached task:

```sh
JAVA_HOME=/opt/homebrew/opt/openjdk@21 ./gradlew :sender:generateReleaseBaselineProfile
JAVA_HOME=/opt/homebrew/opt/openjdk@21 ./gradlew :receiver:generateReleaseBaselineProfile
```

`dexLayoutOptimization = true` is set on both consumers so R8 lays startup classes
contiguously. The sibling `baselineProfileRulesRewrite` flag is deliberately left unset:
it writes the `android.experimental.art-profile-r8-rewriting` module property, which AGP
9.3.0 no longer defines.

Turning R8 on made two name-based dependencies load-bearing. `PlaybackFailureClassifier`
compares `cause.javaClass.name` against the literal
`androidx.media3.exoplayer.source.UnrecognizedInputFormatException`, so the receiver's
`proguard-rules.pro` pins that name; renaming it would silently reclassify every container
rejection as `MALFORMED_MEDIA`. Both modules also keep all `Throwable` names, because
`FlickLog` records `e.javaClass.simpleName` and the phone's Diagnostics sheet shows those
lines to the user. The remaining rules keep Ktor, kotlinx-coroutines, the slf4j-simple
service provider, ML Kit's bundled barcode runtime, and ZXing, and silence the JVM-only
classpath references that Guava, CameraX, Coil/OkHttp and ML Kit drag in.

## Architecture

```text
phone (:sender)                                           TV (:receiver)
content:// media ── CastServerService ── HTTP ranges ──> Media3 hardware decoder
       ^                   :8080 /v/<token>                    ^
       |             (+ :8080 /s/<token> subtitle)             |
       |                  exact owned peer IP                   |
       └──── application CastCoordinator <── WebSocket v2 ──────┘
                                                    control server
```

The sender's Ktor CIO media server reads directly from a `ParcelFileDescriptor`/`FileChannel`; it does not cache or copy the whole file. The TV's Ktor CIO WebSocket server carries pairing/control/state only and cannot browse files or request arbitrary URLs.

## Optional one-time tips

Flick can offer three fixed, flat-price, one-time Stripe Payment Links: $3, $8, and $15.
They are voluntary tips for the Flick app already provided; no app feature or service is
included and nothing unlocks. The three URLs are read at build time from local properties or
the dedicated environment variables:

| Tier | `local.properties` | CI environment |
|---|---|---|
| $3 | `support.stripe3Url` | `FLICK_SUPPORT_STRIPE_3_URL` |
| $8 | `support.stripe8Url` | `FLICK_SUPPORT_STRIPE_8_URL` |
| $15 | `support.stripe15Url` | `FLICK_SUPPORT_STRIPE_15_URL` |

The catalog is strict all-or-nothing: every URL must be an exact validated
`https://buy.stripe.com/...` link with no credentials, port, query, or fragment, or Flick
renders neither the Settings entry nor the earned Library invitation.

The prompt count advances only at the sender's first-frame commit after the current cast
generation guard. After the threshold, the invitation is claimed synchronously and can appear
only when that same Active cast ends normally and returns to Library (local stop, matching TV
`stopped`, or matching source-server stop). It is never automatic during playback, pairing,
cancellation, failure, generic navigation, or first launch. The claim is persisted before the
transient Library card is shown, so rotation keeps the card through the application-scoped
controller while process death cannot repeat it.

Each option opens its configured URL without parameters, identity, analytics, cast data, or
payment state. Flick launches a Custom Tab first and falls back to a browsable browser intent;
it neither receives payment results nor stores payment data. Stripe must be configured with
three one-time fixed-price links, optional personal-information, shipping-address, and custom
collection switched off, and its support, privacy, and refund policies completed before a link
is supplied to the app. A Payment Link token does not encode its price or recurrence in a form
the APK can verify. Release verification must therefore open all three final links and confirm
that they are live, one-time USD checkouts for exactly $3, $8, and $15 respectively, with no
optional items or upsells, before those URLs are used for a distribution build.

## Media HTTP contract

`CastServerService` creates a fresh 128-bit URL-safe token per start and binds port 8080 on the exact currently owned RFC1918 address observed by the authenticated TV. `MediaHttpServer` publishes URI and token as one immutable atomic session so retargeting cannot mix an old authorization token with a new source.

| Endpoint | Implemented behavior |
|---|---|
| `GET /v/{token}` | Bound-host `Host` check, constant-time token check, identical `404` for absent/wrong session, MIME/length headers, full or single-range streaming, `206`/`416`, malformed-range fallback to full `200`, and at most four concurrent response bodies (`503` beyond the cap). |
| `HEAD /v/{token}` | Same Host/token and range semantics, headers only, outside the body-transfer cap. |
| `GET/HEAD /s/{token}` | The sideloaded external subtitle, under a token independent of the video's. Same bound-host `Host` check, same constant-time compare, same identical `404`. Whole-file `200` only — no `Range` support and no range parser. |

### External subtitles

Android has no way to enumerate sidecar `.srt` files: `READ_MEDIA_VIDEO` does not cover them, MediaStore does not index them, and `MANAGE_EXTERNAL_STORAGE` is Play-policy restricted and is not requested. No subtitle is ever discovered from the filesystem. There are two sources, and the local one is therefore a user grant: a one-shot `ACTION_OPEN_DOCUMENT` pick.

A persisted `ACTION_OPEN_DOCUMENT_TREE` folder grant, matched by filename, used to be a third. It was retired because two local sources asked the viewer to understand the difference between granting a file and granting a folder to get the same subtitle attached. Retiring it is not only a UI deletion: that grant persists and nothing expires it, so with the tab gone no surface could hand it back. Releasing it is therefore the application's job and not a screen's: `FlickApplication.onCreate` starts `releaseRetiredSubtitleFolder` once per process, which hands the tree back and then forgets the preference naming it — in that order, because afterwards there is no URI left to release. It runs on `Dispatchers.IO`, so nothing about it is on the path to the first frame, and on a phone that never granted a folder the whole cost is one preference read answering null. Leaving it on the sheet made expiry conditional on opening a screen that no longer has anything to say about it.

The other is an OpenSubtitles download (`net/OpenSubtitlesClient.kt`, wire rules in `net/OpenSubtitlesWire.kt`, surfaced by `ui/screens/SubtitlesSheet.kt`). A search runs two `/subtitles` queries and merges them: one on a hash of the video file itself (`media/MovieHash.kt`) where the file can be read, one on the title plus optional `season_number`/`episode_number`. Hash answers rank first, because the hash names *this* file and a hit is therefore already in sync with it; the hash half is also the one allowed to fail quietly, so a hash the server has never seen leaves the text results untouched. The video never leaves the phone — the hash is computed locally and the hash string is the only thing derived from the file that is sent.

The API key identifies the *app*. An optional user sign-in is offered only so downloads count against that account's own daily allowance instead of the single app-wide quota; the returned session token is kept in this app's prefs and the raw account password is not stored. `download` resolves a link, requires it to be on OpenSubtitles' own domains (`downloadLinkIsAllowed` — an address anywhere else is a distinct refused outcome, never a fetch, so the API cannot bounce the download to an arbitrary host), and writes the bytes into this app's `cacheDir`. What it returns is an ordinary `file://` Uri, so a downloaded subtitle rejoins the picked-file path at exactly the point a picked file does and gets no privileged treatment: same `ServedSession` publish, same independent token, same 5 MiB `/s/{token}` ceiling, same extension-keyed content type, same `MediaUrlValidator` check on the receiver.

The subtitle `(uri, token)` pair lives **inside** the same atomically published immutable `ServedSession` as the video's, so a retarget can never be observed half-applied and a subtitle can never be observed paired with a different video. `MediaHttpServer.setSubtitle` mutates that session under the same lock as `start`/`stop` and lands as one atomic publish, so attaching, swapping or revoking a subtitle never interrupts the video stream. The subtitle token is minted by the same `SecureRandom` 128-bit URL-safe generator as the video token; a new selection mints a new one and revoking or tearing down the socket retires it, so a leaked `/s/{token}` stops resolving.

`/s/{token}` is capped at 5 MiB and refuses anything larger — and anything whose size the provider will not report — with the same byte-identical `404`, so the route cannot be turned into a bulk file-exfiltration path. The ceiling is re-checked against the bytes actually produced, not just the declared size. Content type is keyed off the file's own extension (`.srt` → `application/x-subrip`, `.vtt`/`.webvtt` → `text/vtt`, everything else `text/plain`) because DocumentsProviders routinely declare `application/octet-stream` for both and Media3 selects its parser from what the sender sends.

`loadMedia` gains three optional fields, present **only** when the user actually selected an external subtitle:

```json
{"t":"loadMedia","v":2,"castId":"<id>","url":"http://<phone-ip>:8080/v/<token>",
 "title":"<title>","durationMs":0,"startMs":0,
 "subUrl":"http://<phone-ip>:8080/s/<token>","subLabel":"<label>","subLang":"<bcp-47>"}
```

`subUrl` is always the same host and port as `url` — the sender checks the shared origin before emitting it and omits it otherwise. `subLabel` goes through the same `normalizedLabel(…, 200)` canonicalization as every other wire label. `subLang` is omitted entirely unless the tag is well-formed BCP-47; the sender never guesses one. With no subtitle selected the frame is **byte-identical** to what it has always been, which is what keeps an un-updated receiver playing ordinary media and keeps `v=2` honest. If the optional fields would push the frame past the frozen 16 KiB cap, the sender drops the fields, never the frame.

The receiver validates `subUrl` through the same `MediaUrlValidator` rules as the media URL (same host, same port, no redirect, no scheme change) and fails the cast on a bad one rather than silently fetching or dropping it. It attaches the file as a real Media3 `SubtitleConfiguration`, so it surfaces as an ordinary text track that the existing `subtitleTracksFrom` mapping and the TV subtitles panel already handle. External text loads do not inherit the video's roughly 100-second LAN retry budget: after Media3's ordinary fatal classification they get one 250 ms retry, then stop. The video and audio paths retain the full direct-play retry policy.

Selecting or clearing a subtitle mid-cast re-arms the capability and re-issues `loadMedia` for the **same** `castId` at the position the TV last confirmed. Control ownership classifies a repeat of the live cast as a duplicate, which is otherwise answered from the retained result; the receiver therefore compares the frame's validated subtitle triple against what the running session was prepared with and, only when it differs, re-prepares with the new (or removed) `SubtitleConfiguration` instead of replaying. An identical repeat still replays, so an ordinary retransmit never costs a re-buffer, and a reload is only ever taken from the lease that already owns the cast. Only a generation that still owns the socket may repoint the capability, so a late intent from a superseded cast cannot re-arm a revoked one.

**A reload of a cast that is already Active is not a load transaction.** `SessionController.onReloadMedia` holds the stage at `Active` and calls `PlayerController.reloadInPlace`, which re-prepares the **same** ExoPlayer instance — `setMediaItem(item, resetPosition = false)`, seek to the player's own current position, `prepare()` — and restores `playWhenReady`. The instance, the surface it is presenting to, the `MediaSession` that owns platform media buttons and the track-selection parameters all survive, so the swap costs a re-buffer and nothing else. The one selection state it does overrule is a suppressed text renderer: a sideloaded track arrives under `SELECTION_FLAG_DEFAULT`, which the panel's Off row and any earlier per-group override both outrank, so attaching a subtitle clears text overrides and re-enables the text track type — a fresh player used to discard those along with everything else, and reusing one must not turn a just-attached subtitle into a track that draws nothing.

The in-place reload has a one-shot 12-second subtitle watchdog, deliberately shorter than the control socket's missing-pong floor. A reload is healthy only after the same generation reaches `STATE_READY`, the exact rebuilt `MediaItem` renders a first frame on the existing surface, and Media3 reports the current subtitle URI fully loaded. This applies while paused too: `playWhenReady` remains false, but `READY` alone is not proof that the picture survived. If those three signals never converge, the receiver re-prepares that same player once at its current position without the optional subtitle; it never spends the video's recovery budget or enters a second loop. The rollback is reported back to `SessionController` with the media generation and exact subtitle, so only the still-current prepared subtitle is cleared: the same selection may be retried, while a late callback cannot rewrite a newer subtitle or cast.

Routing that through `beginLoad` instead is what made attaching *or removing* a subtitle kill the cast, reproduced on a Google TV Streamer. `beginLoad` arms the 18 s startup deadline and sets the stage to `Checking`, which `playerSurfaceMode` maps to `CoveredConnecting` — so the UI rebuilt the `PlayerView`'s `SurfaceView` (four surface handles inside 250 ms) at the same moment `playStartup` released the player that was presenting. The replacement's video renderer landed on a surface that never presented, `onRenderedFirstFrame` never fired at all, and since that frame is the deadline's **only** disarm path, a healthy cast died 18 s later reporting `startup_timeout`. Staying `Active` is therefore the fix rather than an optimisation: the surface mode never leaves `VisiblePlayback` and no startup deadline is armed. A subtitle reload that fails explicitly or silently is handled by the subtitle-only rollback above; other steady-state playback failures retain the ordinary bounded recovery and classified `error` path with `beforeReady=false`. The full load stays reserved for a genuinely new cast, and for the contradictory case of a reload arriving with no live player at all, where the startup transaction is the correct one.

A sideloaded subtitle belongs to the title it was picked for. A live cast owns the file it is serving, so browsing the library mid-cast cannot clear the selection; the sender instead re-checks that ownership when the next cast starts and drops a selection made for a different item, rather than attaching one film's cues to another under `SELECTION_FLAG_DEFAULT`.

### Readable video names and online search

Phone Settings has a default-on **Readable video names** preference. It changes presentation only: Flick never renames, moves, or rewrites a video. Every phone surface that presents a `MediaItem` title and the `title` sent to the TV on a new or subtitle-triggered reload use the same live preference. Serving, URI identity, folder scope, sidecar matching, and filename parsing continue to use MediaStore's original display name. Turning the preference off restores that original filename for display, after unsafe control/bidirectional characters are removed; the only persisted value is the boolean choice, never a filename or parsed title.

`VideoNames` is the single pure parser for display and online search. It NFC-normalizes ordinary Unicode without ASCII folding, removes control and filename-spoofing bidi/invisible characters while retaining meaningful script joiners, and strips only the final recognized video extension. A name is simplified beyond that only when it carries release structure: a title followed by a release year and/or `SxxEyy`, a clean trailing parenthesized year such as `Title (2024)`, or by multiple technical tags. Compound release suffixes such as `1080p-WEB-DL` count only as suffix evidence; title hyphens such as `Spider-Man` are never split. The formatter retains title, year, episode marker, apostrophes, hyphens and diacritics; known editions are retained with conservative expansion such as `DC` to `Director's Cut`. Source, resolution, codec, audio, repack, release-group, and site-ad suffixes are presentation noise only. Human titles, arbitrary local kebab/snake names, malformed names, camera/messaging timestamps and counters, UUIDs, and generated IDs take the safe extension-only fallback rather than a guessed title.

The library's own search box searches both of those spellings at once — the name on disk and the title the tile shows — because the user searches for what they were shown. A query is read as words rather than as a substring: `The.Wailing.2016.1080p.BluRay.x265-GRP.mkv` is a tile reading `The Wailing (2016)`, so typing that matched nothing while the dots the user replaced with spaces were still in the string being searched, and no contiguous run of characters reaches across the release junk between `Wailing` and `2016` either. Every word of the query must be found, in any order, anywhere inside the row's text: a half-typed `wail` narrows to `Wailing`, and with the row's word boundaries dropped and the query cut at them, a separator present on one side only cannot make two different videos — `spiderman` reaches `Spider.Man` and `spider man` reaches a file named `Spiderman`. The looser of the two rules is deliberate: in a filter box over one person's own library, failing to show a video they have is the expensive mistake and showing one extra is not, and every further word typed is an AND that tightens the query again. The cost is that a very short word narrows less than it appears to. Titles in scripts written without spaces, which nothing breaks into words at all, are searchable past their opening character for the same reason. The parsed title is indexed beside the raw name, so an `S1E2` on disk answers the `S01E02` on the tile and the release details the tile hides stay searchable. Words are folded by `media/FoldedText.kt` — case with `Locale.ROOT`, NFKD compatibility forms, Latin diacritics and the stroked letters, every non-Latin mark kept — which is one routine shared with the subtitle matcher rather than two that could answer differently about the same film. A query with no words in it returns the scoped list instance itself, and the fold of every name is computed once per library rather than once per keystroke, because Unicode normalization and a filename parse for every row on every character typed is a phone dropping frames under its own typing.

OpenSubtitles search parses the original filename independently of the display toggle, while the subtitles-sheet header uses the current display preference. The complete online pane is keyed by the content URI: changing the cast item disposes its client and coroutine scope, cancels in-flight hash/search/download/sign-in work, and reconstructs query, numeric fields, English language selection, results, quota, errors and credentials UI for the new media identity. Editing any search field cancels the active search, clears its feedback, and increments a generation guard so even a late response cannot populate a newer set of inputs.

The title remains editable, and parsed year (1870–2099), season (1–99), and episode (1–999) are editable, bounded structured parameters. Search language is a non-persisted selector backed by the complete static catalog from OpenSubtitles' `/infos/languages` endpoint; English (`en`) is the default, current regional codes such as `pt-br`, `pt-pt`, `zh-cn`, and `zh-tw` are sent verbatim, and every hash or text request carries the selected language rather than silently broadening to all languages. Search text is NFC-normalized, whitespace-collapsed, and stripped of control/spoofing marks while preserving punctuation, diacritics, and meaningful script joiners. OpenSubtitles' three-code-point minimum is enforced before the wire; a shorter title can still run a hash-only search when a fingerprint exists. Invalid numeric fields disable Search and are never sent.

The movie fingerprint remains the first request. It exists only when Flick has both a valid hash and the positive size used to calculate it; `moviehash_match=only` keeps this first pass exact. The hash and size are one immutable value: descriptor `statSize` wins, MediaStore size is only a fallback, and the search cannot pair a hash with a stale hint or send a hash without `moviebytesize`. A renamed or imperfectly parsed title is deliberately **not** attached to that request, so text can never filter out an exact-file match. An exact answer is authoritative and skips the weaker text request; an empty answer falls back to the normalized text query. The fallback adds `type=episode` only when both season and episode are valid — a year alone does not prove that a file is a movie — then merges and deduplicates with hash results first. An episode request omits year: the year in `Doctor.Who.2005.S14E01` identifies the series incarnation, while OpenSubtitles' `year` filter means the episode's air year and would exclude the correct S14 result. Text results are then judged on *which work they are about*, because OpenSubtitles' own guidance is that `query` is error-prone and that an id — the one thing a phone holding nothing but a filename lacks — should be sent in its place. `feature_details` already carries the answer and was previously discarded: the catalogue title, the decorated `movie_name`, an episode's `parent_title`, the feature type and the year. `OpenSubtitlesMatchPolicy` (`net/OpenSubtitlesMatchPolicy.kt`) compares the normalized query against those names with case, accents, compatibility forms, punctuation, joiners and a leading article folded away, while keeping every non-Latin mark, because an Indic vowel sign or virama is a letter of its title rather than decoration on it. Three foldings exist because release names and catalogue entries disagree three specific ways: words are also compared with every boundary between them removed, since a scene name drops the apostrophe of `Ocean's Eleven` and keeps the hyphen of `Spider-Man` that the catalogue may not; roman numerals fold to arabic, since `Rocky.2` and `Rocky II` are one film; and the Latin letters carrying their mark inside the glyph (`ø ł đ ð ħ ŧ ı ß æ œ þ`), which no decomposition separates, fold explicitly. A parent title answers only an episode query: comparing a series name against a film's filename is exactly how a long-running series' download counts buried the 2008 film that shares its name. Agreement on the work outranks agreement on the kind of work, which outranks year/season/episode agreement, which outranks every quality signal — and `type=movie` is still never sent, so the film-versus-episode preference stays a ranking decision that cannot filter a badly named episode off the wire. A text result naming a different work is dropped, but **only beside a positive identification** — a result that actually agrees, never one that merely failed to conflict. A row naming no feature at all, or sharing only a leading word, is evidence of nothing: gating on those would delete `Rambo.2`, filed as `Rambo: First Blood Part II`, in favour of the 2008 `Rambo`. Whole classes of title disagree innocently — transliterations, original-language names, numbering conventions — and losing a search to one would be a worse failure than the one being fixed. Exact-file results do not second-guess their stronger hash with fallible catalog metadata, and are never judged on a title that may be a rename. Each class then prefers complete subtitles, human translations and trusted sources before using rating, votes and downloads to finish otherwise equal ties. Missing feature metadata is neutral and an explicit conflict ranks last. A page is parsed past the thirty-row cap and ranked before it is cut, so a fuzzy answer that leads with the wrong work can no longer push the right one off the end. Rows state the work each subtitle is filed under alongside the exact-file, trusted, AI/machine, foreign-only, SDH, feature, rating and download signals, instead of hiding why one result ranks above another. The request normalizer still sorts parameters by name, lower-cases with `Locale.ROOT`, and leaves spaces for the caller's canonical `+` encoding. Opaque generated/camera/messaging IDs and names made only of technical tags do not auto-fill a low-signal text title, but their file hash may still search them. No search is sent until the user presses Search: the exact pass sends selected language plus the optional atomic hash/positive size, while the fallback sends only the normalized parsed title, valid non-episode year or season/episode, inferred episode type and selected language. A raw filename or path never leaves the device.

The service uses `WIFI_MODE_FULL_HIGH_PERF` and a six-hour-bounded partial wake lock while it owns the source. Its foreground notification is the phone's media notification — see [The phone's media notification](#the-phones-media-notification) — and every intent it carries is unique and immutable per `castId`. Latest-start/resource ownership gates prevent delayed A startup/failure/stop from publishing, releasing, or stopping B. `START_NOT_STICKY` and unknown intents never reconstruct a cast.

## Control port selection

The control port is durable, persisted, and has a fixed default. An ephemeral port (`0`) meant every restart bound a different number: the port printed on the pairing screen went stale before the user finished typing it, the phone's persisted `port_<host>` was dead on every resume, and cached mDNS SRV records named a closed port.

`DEFAULT_CONTROL_PORT = 47654` sits in the dynamic range and is deliberately clear of Cast's 8008/8009/8010 and of the sender's media port 8080. `ControlServer.start(host, ports)` walks the ladder in order:

1. the port persisted from the last **successful** bind;
2. `47654`;
3. `47655..47663`, on `BindException`;
4. `0` (ephemeral), as an absolute last resort so a hostile or unlucky collision on every fixed port can never make the TV undiscoverable.

The receiver persists, advertises and renders the port that **actually bound**, never the one requested, and logs which tier won (`[bind] started host=<tv-lan-ip> port=<port> tier=persisted|default|ladder|ephemeral`). A failed candidate is logged at `w` rather than swallowed — silently absorbing `BindException` is exactly what would make a fixed-port strategy fail invisibly.

`reuseAddress = true` is set on the CIO engine. It defaults to **false** in Ktor 3.1.3, so a same-port rebind throws `EADDRINUSE` while a prior peer socket lingers in `TIME_WAIT` — which a durable fixed port hits on every restart. The bind host remains the specific site-local IPv4 from `LanAddress.current()`, never `0.0.0.0`, and the anti-rebinding `Host` pin still compares the exact bound `host:port`.

The binding is one immutable `(engine, host, port)` tuple published only after the engine has started; a socket accepted inside that publication window waits up to two seconds for it rather than being rejected. Engine start/stop run on `Dispatchers.IO` via `startSuspend`/`stopSuspend`; the blocking `start(Boolean)`/`stop(Long, Long)` bridges would hold the caller for up to ~1.1 s.

Connectivity callbacks are re-sample triggers, not rebind events. `LanBindingMonitor` reports an **address**; `onCapabilitiesChanged` fires for RSSI, link speed, validation and `NOT_SUSPENDED` on a link that never changed address, and those updates carry no address at all. A single reconciler owns bind state, is woken by the distinct address flow with a slow 10 s safety-net tick, and resolves a capability burst on an unchanged address to "do nothing".

A visibility change (screensaver, Home, a system dialog) no longer tears anything down. `ON_STOP` releases the decoder, publishes an idle frame, sends the `tv_backgrounded` terminal and closes the pairing surface, then **re-advertises with TXT `state=sleeping` while keeping the socket bound and the service registered**. `ReceiverBindingGate` already refuses `loadMedia` while backgrounded, so the posture is unchanged: the socket stops accepting new casts instead of vanishing. `ON_START` re-advertises `state=ready` on the still-live port. NSD has no update primitive, so a state flip re-registers under the **same service name and the same port**; the sender must treat a same-name re-registration as an update, never as a loss.

## Launch and initial pairing

The TV QR payload is

```text
flick://pair?v=4&h=<tv-lan-ip>&p=<port>&c=<four-digit-code>
```

with exactly the parameter set `{v,h,p,c}` in any order, no user-info, no URI port, no path and no fragment. **The four-digit code IS in the QR**, as of 2026-07-28 and by the product owner's explicit decision — see `docs/design/control-channel.md` §2 for the reasoning and for what it costs. The short version: the TV already prints the code beside the QR, so line of sight always sufficed; what is new is that a browsable deep link can now hand a live code to a system scanner. The code's five-minute TTL, its validity only while the pairing surface is rendered, and the five-failure lockout are therefore load-bearing.

Because the payload carries the code, the QR is re-encoded on every code rotation rather than being emitted once. The QR is emitted only while a real binding exists (host non-blank and port in `1..65535`); there is never an `h=`/`p=` placeholder. `flick://pair?v=3` remains valid as an endpoint prefill whose code is still typed, and the bare `flick://pair?v=2` as a launch-only envelope, so neither an un-updated TV nor an un-updated phone is stranded.

**A `c=` is honoured only from Flick's own camera.** The two ingresses are not equivalent and the asymmetry is structural, not a flag: `PairLaunchParseResult.Valid` — what any externally delivered URI resolves to — has no field for a code, and `ScannedPairLaunch`, which does, is built solely by `PairLaunch.parseScanned`, whose only caller is the in-app scanner. See `docs/design/control-channel.md` §2 for the local-impostor attack this closes.

The sender's `singleTask` activity routes both `onCreate` and `onNewIntent` through one ingress on the **untrusted** parser. It copies the URI locally, clears both incoming and stored intent data synchronously, parses only the copy, and publishes an unsaved process-local event. It validates `h` with `isCanonicalIpv4`, `p` with `isCanonicalPort` and `c` as exactly four ASCII digits, treating any failure as an invalid QR — a malformed `v=4` is rejected whole rather than salvaged into a prefill. An Intent-delivered `v=4` is then **demoted to a `v=3` prefill**: host and port fill the manual form, the code is dropped in the parser, and the four digits are typed as before.

Only a payload the in-app scanner read reaches the confirmation card, where the TV is named and **only that explicit action dials** — a scan still never auto-connects. The ingress logs the scheme and host and nothing else: with `c` present, a log line that echoed the URI would be a disclosed credential, and `ScannedPairLaunch` overrides `toString` for the same reason.

Host entry accepts canonical dotted-decimal RFC1918 IPv4 only; port is canonical decimal `1..65535`; code is exactly four ASCII digits. Manual Connect uses the same full form, pre-filled with `47654` as a default only — it is never dialed blind and never overrides a QR- or NSD-supplied port. Unpaired NSD results are advisory and cannot supply a target.

The sender opens the typed endpoint and sends `negotiate(v=2,minV=2,maxV=2)` with a fresh nonce. It sends `pair` only after the exact strict `negotiated` response, so an old receiver cannot consume the code during version detection. A valid `paired` result is durable before routing away.

`PairingManager` is the receiver's sole authorization/UI source. An Open code is stable for five minutes, and it is never left valid across a surface that does not render it: closing or hiding the pairing surface drops the code in the same call, and a path that opens one — including a per-phone forget that empties the store — obliges its caller to route the screen to Pair. Four global failures retain it; failure five begins a 30-second lockout, with rounds doubling to an eight-minute maximum. The global round/deadline survives process restart; per-host state is bounded to 32 records and throttles a host for 10 seconds after three failures. Pair success atomically commits key/keyId/date/label plus the last-paired key id, consumes the code, shows 1.5 seconds of Success, then returns to Standby without exposing a replacement code.

**Record encoding.** Credentials live in one `SharedPreferences` StringSet, `pairing_records_v2`. A record is `v3|keyId|key|pairedAtMs|label` — label last, so it may still contain `|`, which label normalization does not strip. The leading `v3` is a version sentinel rather than a field count, because a count cannot tell the shapes apart: the legal v2 label `12345|home` splits into four fields whose third parses as a number, and a migration trusting the count would read a phone called "home" paired in 1970. A keyId is always 22 base64url characters, so no v2 record can begin `v3|`. Legacy `keyId|key|label` records are read in place with an **unknown** date — never a guessed one — and the UI says so rather than inventing one; they are never rewritten, so an existing pairing survives the upgrade without re-pairing. A v3 record whose date is corrupt keeps its credential and loses only the date. The set has no order, so the Settings list sorts dated records newest-first, then undated ones by label, with the key id as a final tiebreak, giving a total order that is identical on every read.

### Peer identity

The authenticated peer is read from `call.request.local.remoteAddress`, never `call.request.origin.remoteHost`.

`remoteHost` resolves `InetSocketAddress.getHostName()` — a **synchronous reverse-DNS (PTR) query** on the LAN. Most consumer and ISP routers run dnsmasq and answer PTR for DHCP clients, so on those networks it returns a hostname such as `some-phone.lan`. That value failed the private-IPv4 gate and closed every legitimate phone's socket before one protocol frame was read, with no log and no `denied` frame; it was also published as `peerIp` in `paired`/`resumeChallenge`/`resumed` and is field 8 of the resume HMAC transcript, which the sender validates as an IPv4 literal. `remoteAddress` uses `getHostString()` and never resolves. `local` is used rather than `origin` because `origin` is overridable by a `Forwarded`/`XForwardedHeaders` plugin, while `local` is always the CIO connection point derived from the accepted socket. When the socket address is null Ktor returns the literal `"unknown"`, which correctly fails the gate — fail-closed is intended.

Using a non-resolving, non-header-derived identity strengthens the posture: `remoteHost` was a resolver-controlled string feeding per-host pairing throttling and the HMAC transcript.

The receiver caps unauthenticated WebSockets at four and applies a six-second auth deadline. Malformed pre-auth input has a three-frame budget. Both sides enforce the 16 KiB decoded frame cap, unfragmented UTF-8 text/object input, duplicate/trailing-data rejection, exact fields/types/ranges, and no unknown v2 message types. Device, TV, and title labels are normalized to canonical single-line values before sending; the receiver rejects noncanonical control/format/whitespace variants rather than silently changing an authorization transcript or command.

A `denied` frame carries a coarse diagnostic reason: `{"t":"denied","v":2,"reason":"<enum>"}` over exactly `code`, `expired`, `surface`, `locked`, `busy`, `storage`, `proof`, `unknown`. Only `code` and `expired` are code-derived, so the frame stays non-enumerating — it is no oracle for guessing a key id, a device, or whether a TV has ever been paired. The sender accepts both the legacy two-key form (an un-updated receiver) and the three-key form, and maps each reason to distinct copy.

Closing/hiding the pairing surface invalidates its open generation immediately; a late pair attempt is denied with `reason=surface`. TV Settings implements confirmed **Forget all phones**: it stops/revokes the active controller, clears credentials only after the durable write succeeds, resets throttle/lockout state, and reopens visible first-run pairing.

TV Settings also lists each paired phone by name and pairing date and offers a per-phone **Forget**, likewise two-press confirmed — armed per key id, and disarmed the moment the D-pad leaves that row. `PairingManager.forget(keyId)` removes exactly one record on the same durable-write-first discipline and returns false when nothing was removed, so the UI can never report a forget that did not happen. Removing one phone deliberately does **not** open a pairing code: a code is an authorization surface, and removing one of several phones is not a request to admit a new one. Reaching zero records is the exception and takes the Forget-all path exactly, lockout reset included, so a TV cannot be left with no phones and no way to re-pair while a lockout still runs — and because that path opens a code, `ReceiverApp` closes Settings when the last phone goes, exactly as Forget all does. It has to: the surface router gives Settings priority over Pair, so leaving it open would leave a code that is valid, rotating and accepting attempts while nothing on screen renders it. With no phones there is no list left to show either, and the router then falls to `pairedCount == 0 → Pair`, which renders the code. `last_device` — what Idle renders as "Paired with …" — is recomputed whenever the forgotten phone was the one it named, promoting the newest remaining phone or clearing the name outright; a store written before v3 has no last-paired key id and falls back to matching the bare label, which clears a name when two phones share one rather than showing a wrong one. The UI is handed `PairedPhone` (keyId, label, date) and **never** the pairing key. `findKey` reads the same set, so a forgotten phone's next `resumeInit` is denied `unknown_key` — but a resume already past that point is not, which is what the challenge sweep below exists for.

TV and paired-phone renaming share one ordinary single-line Compose text field, so Android TV Gboard supplies both the on-screen keyboard and its built-in voice input; Flick requests no microphone permission and runs no speech recognizer. The editor selects the current name, uses a text keyboard with word capitalization and IME Done, and asks the TV IME for centred placement. That selection is seeded but not trusted: the TV IME collapses it to a caret at the end of the name as soon as it connects, so the first edit is instead applied as though the whole field were still selected — typing replaces the name outright and a delete clears it, after which the field is an ordinary editor and a name can be amended rather than retyped. The buttons are reachable with a remote: the editor consumes DirectionDown as a cursor move, so the field claims that key-down ahead of the editor and moves focus to Cancel, while up from either button returns to the field and left/right stay cursor movement inside the text. Input and saved names share the 80-Unicode-code-point wire ceiling, and the cap uses code-point offsets so a surrogate pair is never split — including the run recovered from that first edit. Blank canonical input cannot save; Cancel and Back do not write. A failed save is only cleared by a real text change, never by the IME session ending as the save is made. Opening the editor from Pair first closes that authorization surface, then reopens it on exit, so neither a live code nor an on-TV confirmation can be hidden under the modal. A successful TV rename updates the durable preference, the visible state, and the active NSD registration. A paired-phone save calls `PairingManager.rename`, whose record rewrite preserves key id, key, pairing date, last-device tracking, and any live authenticated session.

Forgetting the focused row also has to say where the D-pad goes, because a `LazyColumn` item that is disposed takes focus with it. The landing is the row below, the row above when it was the last, and **Device name** when there was no other phone at all — one paired phone is the common state, not an edge case, and a landing of "nowhere" leaves the remote steering a screen it cannot move on, recoverable only with Back. It is expressed as a state (`SettingsFocusReturn.Phone` / `DeviceName`) rather than as a nullable key id precisely so that fallback is reachable instead of collapsing into "nothing owed". The request is driven off the ARRIVAL of the new list rather than off the press, and repeated across frames (`landTvFocus`), because the replacement row is not attached and placed in the frame that removed the old one.

**Forgetting the connected phone.** `ControlServer.forget(keyId)` also ends that phone's live session, but only that phone's: `Connection` carries the key id it authenticated with, and the revoke is gated on it, so forgetting phone B never drops phone A off a running film. The identity test and the lease clear happen under one hold of `serverLock` and compare the connection **object**, not the key id — `active` is `@Volatile` and an idle replacement can install a different socket between any test and any separate mutation, so a single early read followed by an unconditional clear would still drop that replacement. A live cast is stopped through the player before the socket closes, because the revoke invalidates the lease and a film left decoding past that point has no owner left to stop it and no socket to report `stopped` on; a phone that is merely connected has no cast and needs only the revoke.

The order is deliberately the **inverse** of Forget-all: the durable write goes first, then the socket work. Forget-all is all-or-nothing and closes the screen, so revoking first costs nothing; per-phone forget returns a value that drives a row which stays on screen, and revoking first would let a rejected write report "nothing happened" to a user whose casting phone had in fact just been cut off. Writing first makes `false` mean nothing happened. The cost is the microseconds between the write and the revoke, in which an already authenticated socket stays authenticated — it gains no capability it did not already hold, and a cast started in that window is still caught because the lease is read after the write.

**Removing the record is not by itself enough to stop re-authentication.** `authenticate` reads the credential once, at `resumeInit`, and validates `resumeProof` against that cached copy; the store is never read again, and nothing re-checks a live connection's key id afterwards. A phone whose `resumeInit` landed before the write therefore completes its proof afterwards against a record the TV no longer has, and installs itself as the controller — for the whole `resumeInit → resumeProof` round trip, up to the six-second auth deadline, and deterministically for a hostile paired phone, which may keep spare half-finished handshakes open within the four-connection pre-auth cap and complete one after each Forget. So each forget marks the handshakes instead: a `resumeInit` registers a `@Volatile` ticket for the key id it claims **before** `findKey` is called, `ControlServer.forget` sweeps that registry **after** the durable write and **before** it reads the lease, and the lease install reads the ticket under `serverLock`. The four orderings are exhaustive — a handshake already registered is marked; one registered after the sweep reads a store the write has already changed; one that installs in between is found by the lease read; and the `pair` path carries no ticket at all, so a record `attemptPair` has just committed still installs. Forget-all runs the same sweep after its clear, and re-reads the lease behind it, because a durable commit is not instantaneous.

The sweep touches no lock, and that is a requirement rather than an optimization: `ControlServer.forget` acquires the `PairingManager` monitor and then `serverLock`, so re-reading `PairingManager` from inside the install block — the obvious fix — would acquire `serverLock` → manager monitor and give the control server an AB-BA deadlock. A refused install answers `denied reason=proof`, which is what the phone's next connection would get from the missing record anyway, so the frame enumerates nothing new; `busy` is deliberately not reused, because `busy` is an invitation to retry.

## Resume, discovery, and persistence

The receiver persists a random non-secret `tvId` and advertises `_flick._tcp.` with actual port plus TXT `v=2`, `id`, model, and state. The sender treats all resolved values as candidates. It tries the last mutually verified endpoint first, then at most three same-`tvId` candidates in deterministic host/port order.

Resume uses fresh 128-bit client/server nonces and HmacSHA256 over the frozen versioned, role-separated, length-prefixed transcript. The receiver consumes one challenge and compares the client proof in constant time. The sender verifies the server proof before marking the socket authenticated or committing endpoint/name changes. The 256-bit pairing key is transmitted only by initial `paired`, never by resume.

An unauthenticated denial cannot erase key bytes. If all bounded candidates fail authentication/protocol verification, the record is marked `needsRepair` and automatic retry is suppressed; transport-only failure retains it for explicit retry. Replacing a v2 key tombstones the superseded key ID.

Legacy v1 host records are handled conservatively. The sender can identify a canonical stored host and derive the deterministic non-secret legacy key ID locally, but it sends no legacy key or proof and performs no automatic challenge migration because the receiver has no safe legacy TV-ID lookup. The user re-pairs with current TV-displayed values. Only a successful visible v2 pair at the exact stored host writes the migration marker and retires that legacy record; a changed host always requires visible re-pairing and leaves no proof spray across discovery candidates.

After either initial pairing or resume, the sender waits 250 ms for the receiver's immediate `busy(active_cast)` disposition. A busy result after a successful initial pair is represented internally as `PairedBusy` so the newly issued key/endpoint is durably preserved before the user sees the busy failure. Accepted residual P2: v2 has no positive `available` frame, so silence after 250 ms is treated as available. A late busy can cause brief sender UI/foreground-service churn, but receiver ownership is decided independently under its mutex and the second phone cannot take the cast. A future protocol revision may add an explicit `available|busy` result.

NSD failures clear listener state and schedule one bounded retry with the error code logged; stop cancels it. On TV, connectivity callbacks re-sample the address and the reconciler tears down control/cast/NSD only when the site-local IPv4 is actually **lost or different**, then binds and advertises a fresh endpoint while foregrounded. An unchanged address produces no rebind, whatever the callback said.

## Cast ownership and sender startup

`FlickApplication` owns one main-immediate application scope and one `CastCoordinator`. Activities/Composables observe its flows and forward events; they do not own the cast/control socket. One pairing-attempt generation and one cast job prevent stale completions from committing.

Each Flick action creates a random 128-bit `castId` and:

1. Uses an authenticated v2 socket, resuming the saved pairing first if necessary.
2. Confirms receiver-observed `peerIp` is still owned by an up, non-loopback phone interface.
3. Requires a `content:` item with positive known size; starts the source service for that cast and waits up to nine seconds for matching RUNNING/ERROR.
4. Registers `loadAccepted`/`loadReady` waiters, sends `loadMedia`, waits up to two seconds for acceptance, then up to 18 more seconds for first-frame readiness.
5. Enters Now Playing only when the matching current-generation `loadReady` arrives.

The sender keeps up to 100 device-local playback checkpoints in one Preferences DataStore. A checkpoint is keyed by a hash of the content URI and MediaStore source revision, is written only from matching Active-cast TV-confirmed state, and is coalesced to five-second position intervals with pause/cleanup flushes. Positions before 10 seconds, within 30 seconds of the end, or reported as ended are cleared. Detail waits for the initial DataStore read, then offers **Resume from _time_** and a separate **Start over** action when a checkpoint is eligible. Both the selected start and its item travel as one cast request through control reconnect and retry. Retrying a cast that had reached Active resumes from the latest TV-confirmed position, clamped to the MediaStore duration the retry's own `loadMedia` carries rather than to the container duration that decided eligibility — the two disagree on a mis-scanned or VFR file, and the receiver answers `startMs > durationMs` by closing the control socket, turning a retryable failure into a dead cast. Start over retains the old checkpoint until `loadReady` proves its first frame, so a failed restart cannot destroy a valid resume point. A failed read retries on a doubling backoff capped at a minute rather than ending the flow, because a `catch` would pin the state at its fail-open empty value for the life of the process and silently retire the feature; the first failure still publishes that empty value so Detail's actions stop waiting. Every queued write is acknowledged exactly once whatever the store does — an unacknowledged write would hold the recorder's single-flight slot and stop all later checkpoints. The DataStore is excluded from backup and device transfer because its hashed identities still describe media revisions on this phone.

That eligibility rule is now **one function**, `media/ResumeProgress.kt`'s `resumePositionMs(state, fingerprint, durationMs)`, because it has two surfaces rather than one: Detail's **Resume from _time_** CTA and the amber line the library tile draws along the bottom edge of its still. `CastCoordinator.resumePosition` delegates to it and `resumeProgress` adds exactly one further guard, so a tile that draws a line for a resume the sheet would not offer is unrepresentable rather than merely untested. **The one asymmetry is deliberate and is the whole of that guard**: a file MediaStore never measured a duration for still *offers* a resume — a checkpoint is a position and a position needs no denominator — but draws no line, because a fraction against an unknown duration would be a guess. Denying the resume instead would cost a real feature over a MediaStore quirk. The tile's line is `spark` on a white 30% track rather than a dark one, for the same reason the tile's ripple is `spark`: the poster scrim already lays 62% black under that edge, so a dark track would vanish on exactly the near-black stills it has to survive. The grid is kept off the checkpoint clock by never unwrapping the progress `State` at grid scope — `LibraryScreen` threads the `State` itself into each tile, which derives its own `ResumeProgress` under `structuralEqualityPolicy`, so a five-second checkpoint republish invalidates only the tile whose own value moved.

Detail's two escapes from the CTA are one row of tonal pills under it rather than two stacked full-width text links: **Start over** and **Play on this phone**, at intrinsic height so a wrapped label cannot leave them at different heights. With no checkpoint there is nothing to start over from, so that pill is **withheld** rather than disabled — a dead control is a promise the sheet cannot keep — and the phone action takes the row on its own weight.

Every non-ready path invalidates the cast generation, cancels waiters, best-effort sends `cancelLoad`, and sends a cast-correlated service Stop. The service clears its atomic media session and releases its socket/locks only when that generation still owns them. Retry is user initiated and creates a new cast ID/token.

Once Active, phone navigation is independent from cast ownership. The explicit downward minimize action and system Back route Now Playing to Library without sending `stop`, cancelling the cast job, or releasing the source service. Library renders a cast-backed mini-player that restores controls only while the same current `castId` remains Active. Android partial video access exposes a persistent user-triggered **Add videos** action; full MediaStore access exposes **Refresh**. Media queries are cancellation- and generation-gated so a stale result cannot republish videos after reselection or revocation.

### The phone's media notification

The foreground-service notification is a real media notification: it lands in the Android media-controls area with a working seek bar, −10s / play-pause / +10s in the collapsed row, and Stop, and it drives playback **on the TV**. This is a phone-side change only — no wire frame, no capability, no receiver code.

`CastServerService` remains the foreground service. It is deliberately **not** converted to a `MediaSessionService`: `LatestStartGate`, `GenerationResourceOwnership`, `teardownGuard` and the rule that a stale generation may never remove the notification or stop a newer cast are the most delicate code in the module, and a second lifecycle owner over the same instance would have to reproduce all of it. The service instead builds one `MediaSession` (`androidx.media3:media3-session:1.10.1`, the version the receiver already runs) over `CastRemotePlayer` and styles the notification with `MediaStyleNotificationHelper.MediaStyle`.

`CastRemotePlayer` is a `SimpleBasePlayer`, which exists for exactly this shape of app — a controller with no decoder of its own. **It re-implements no transport.** `handleSetPlayWhenReady`, `handleSeek` and `handleStop` forward to the same `PlaybackSession` the on-screen remote spends, so the coalescing of a ±10s run into one seek, the optimistic play/pause hold against stale in-flight `state` frames, and the idempotent absolute seek are single-sourced. `handleSeek` branches on the *command tag* rather than on the position: `COMMAND_SEEK_BACK`/`COMMAND_SEEK_FORWARD` (both 10 s) reach `PlaybackSession.skip(±10_000)` and therefore still join a burst — five taps in the shade cost the TV one decoder flush, not five — while a scrubber landing, which has no run to join, reaches the new `PlaybackSession.seekTo`. That verb is the `beginSeek` the drag's `scrubTo`/`scrubEnd` pair already ends on, taken once instead of twice; `SeekPolicy.seekTarget` clamps it on the same terms as `skipTarget`, leaving an unknown duration to the receiver rather than guessing one.

Main-confinement is structural rather than conventional: the player's application looper **is** the main looper, Media3 raises on a `Player` touched from any other thread, and the session those verbs reach is main-confined for the same reason. A notification or binder thread cannot reach `PlaybackSession`'s plain fields.

`CastTransportState` is the process-wide bridge, the same idiom as `ServerStateHolder` and `SubtitleServingState`: the coordinator publishes a `CastTransportSnapshot` and registers the verbs; the service and the player read it. Nothing reaches into `FlickApplication` from the service. The coordinator republishes **synchronously inside every verb**, because the player reads the snapshot back the instant a hook returns — a value arriving one dispatch later would hand the platform the pre-command state and flicker the play/pause button back to what it was.

What the scrubber needs is specific and all of it is supplied: `COMMAND_GET_CURRENT_MEDIA_ITEM` and `COMMAND_GET_METADATA` (without them Media3 withholds duration and metadata from the platform session, and the Android 13+ media controls draw no bar at all without a duration), a `MediaItemData` carrying `durationUs` and `isSeekable`, and `COMMAND_SEEK_IN_CURRENT_MEDIA_ITEM`, which is what Media3 converts into `PlaybackStateCompat.ACTION_SEEK_TO` and what makes the bar draggable. The position reported is the **optimistic head**, not the TV-confirmed position, for the same reason the remote's scrub bar draws it. It is extrapolated forward only while the TV says PLAYING and no gesture is holding the head — a BUFFERING frame carries the position the player is filling *toward*, and a held head is where the user is pointing. One `State` is built per snapshot and cached: `PositionSupplier.getExtrapolating` measures from the instant it is constructed, so a fresh one per `getState()` call would restart its clock on every read and leave the scrubber frozen.

The ±10s buttons are Media3 **media-button preferences** backed by `Player.COMMAND_SEEK_BACK`/`COMMAND_SEEK_FORWARD`, not plain notification actions, because that is the only shape the Android 13+ media controls render: that surface builds its own five-slot layout out of the session's playback state, and only `PlaybackStateCompat` custom actions can fill the slots either side of play/pause. Media3 converts a player-command button in the BACK/FORWARD slot into exactly such a custom action and executes it back through `Player.seekBack`/`seekForward`, so a shade tap and a headset button land in the same hook. It also disables a button whose player command the session does not currently offer, which is what makes them disappear on their own while a cast is still connecting. The explicit notification actions (`ACTION_PLAY_PAUSE`, `ACTION_SKIP_BACK`, `ACTION_SKIP_FORWARD`, `ACTION_STOP`, all delivered as ordinary start commands like the existing Stop, and legal from the shade for the same reason it is — the service is already foreground) are the compatibility path for releases whose shade still draws a `MediaStyle` notification itself. The `castId` is in each intent's data URI as well as its extra, because `Intent.filterEquals` — what the platform keys a `PendingIntent` on — never looks at extras.

**Transport is offered only where it does something.** The gate is one predicate: the control socket is CONNECTED *and* the cast has reached `Active`. Before that the receiver has adopted no media; after a terminal there is no cast left to command. Play/pause, ±10s and the scrubber are all withheld outside it — during startup the notification reads "Connecting to *TV*" and offers Stop alone — and the same predicate is re-checked inside each verb, because a hardware media key does not consult a button. Stop is the deliberate exception: it is a local intent to the source service and tears the cast down whether or not the TV is still listening, so it is offered in every state including ENDED and ERROR. A file with no known duration keeps play/pause and ±10s and loses only the bar, since a bar over an unknown length is a fiction. `PlaybackPhase.ERROR` reports IDLE rather than a player error, which also satisfies Media3's rule that a player error is legal only in `STATE_IDLE`.

Re-posting is driven off `CastNotificationPolicy.Shape` — title, TV name, playing, status line, control set — and never off the position: `state` frames arrive several times a second, and the platform advances the scrubber from the session on its own, so re-posting on each one would repaint the shade continuously for nothing. The post itself happens under `teardownGuard`, which is what already serializes the foreground notification with the generation transition, and only while `startGate` still holds a generation; a frame arriving beside a teardown therefore cannot resurrect a notification `STOP_FOREGROUND_REMOVE` has just removed. Every existing removal path is untouched. The `MediaSession` is released in `onDestroy` before its scope, because a live platform session outliving the cast is what leaves a dead transport card on the lock screen; when nothing is casting the player reports `STATE_IDLE` with an empty playlist and no available commands.

**No manifest entry is needed for media buttons, and adding one would break them.** With no manifest `ACTION_MEDIA_BUTTON` receiver and no `MediaSessionService` in the package, Media3 registers its own runtime receiver and points the session's media-button `PendingIntent` at it, so hardware and Bluetooth keys reach the session for exactly as long as the session exists — which is exactly as long as a cast does. `androidx.media3.session.MediaButtonReceiver` is the wrong tool here: it resolves a `MediaSessionService`/`MediaLibraryService` and finds none.

The channel stays `IMPORTANCE_LOW`. The media-controls surface keys on a `MediaStyle` notification carrying a platform session token, never on importance, so raising it would buy the transport nothing and cost an ongoing, silent-by-nature row a sound and heads-up eligibility — and the platform keeps the user's own setting for a channel that already exists, so the change would only ever reach fresh installs. The category becomes `CATEGORY_TRANSPORT`, and visibility `VISIBILITY_PUBLIC` so the controls work from the lock screen. Runtime `POST_NOTIFICATIONS` was already requested at first composition in `MainActivity`, so the notification is visible on API 33+; a refusal costs the notification and never the cast.

**The artwork is the film, and the card's colour comes with it.** A `MediaStyle` notification carrying a session is not drawn as a notification at all — SystemUI lifts it into the media panel, and `MediaControlPanel.bindArtworkAndColors` builds that panel's entire palette from the artwork bitmap via `WallpaperColors.fromBitmap` and Monet's `ColorScheme`: the card's gradient, the transport and progress tints, the text, even the app-icon tint. The notification's own `color` is read nowhere in that path. The still used to be matted on a 448×448 `Spark` square for exactly that reason — the only way to make the panel come out amber was to make the picture amber. **That mat is gone, deliberately.** The card is now painted out of the film, which is the trade taken in exchange for showing the frame at its own aspect ratio instead of shrunk into a ground. `setColorized` is still not set — it buys nothing on a surface that does not draw the notification row, and would paint the session-less fallback row solid amber, which the palette forbids — and `setColor(Spark)` stays, where it still tints the small icon on that fallback path.

`artworkCrop` in `CastArtworkCrop.kt` is the whole geometry, and it is pure arithmetic so the rule is unit-tested without a device. A still keeps its own shape between two aspect bounds and is centre-cropped past them: wider than **16:9** is trimmed to 16:9, taller than **4:3** is trimmed to 4:3, and everything between passes untouched. The band is therefore **landscape end to end** — nothing this composes is ever taller than it is wide. Both bounds exist because every surface that draws this bitmap fills a slot with it and crops the overflow, and none of them can be told not to: the scale type is hard-coded `centerCrop` in the platform's own layouts, and nothing between here and the screen crops to a shape on the app's behalf — `Icon.scaleDownIfNecessary`, `SizeLimitedBitmapLoader` and `MediaMetadata.Builder.scaleBitmap` all scale *uniformly* and never crop. The slots run from square (a notification's right-hand icon at `notification_right_icon_size`, a car head unit) to roughly 2:1 (the shade's media card, `match_parent` by 184dp expanded): pixels outside that band are spent on rows and columns nothing displays, out of a fixed budget, so the waste comes out of the resolution of the part that is seen. Scope (2.39:1) gives up a quarter of its width and a flat 1.85:1 frame 4%. **The tall bound was 3:4 and is now 4:3**, which is the one change with a visible consequence: what a frame keeps of its own height in that ~2:1 card is its aspect over 2, so a 3:4 still showed **37%** of itself where a 4:3 one shows **67%** — the old bound was buying rows the only surface with any size to it always discarded, and leaving the viewer a sliver through the middle of their own clip. It costs the tallest case the most: a 9:16 phone clip now keeps 42% of its height, rows that were being carried rather than seen. The **size** is no longer constant, but the **cost** is: every shape is scaled to fit 448×448 worth of pixels (200,704 px, 802,816 bytes at ARGB_8888) and never upscaled, which is at most what the old square cost and leaves at least 240 KiB of the ~1 MiB Binder ceiling for the rest of the notification. That still matters because the bitmap is parcelled to SystemUI twice — once as the large icon and once in the session metadata, where `LegacyConversions` puts it into `METADATA_KEY_ALBUM_ART` and it outranks the large icon. 16:9 spends the budget as 597×336 and 4:3 — now the most expensive shape there is, since a square still is cropped to the tall bound before it is scaled — as 517×388. Nothing reaches the full 448×448 any more, so the Binder margin only grew. Both shapes outside the band land *inside* the budget rather than on it, because the crop takes them below it and nothing here is ever scaled up to spend one: 2.39:1 arrives as 476×268 and 9:16 as 360×270. The still is decoded into a 640 px square box first — square so the long edge is the bound whichever way the film was shot, and larger than any edge finally drawn because the crop only ever removes pixels. Rounding the scaled edges can carry a pair past the budget, so the long edge gives one back until it fits; `CastArtworkSizeTest` reads the byte cost off the production geometry for every named shape and sweeps 58,400 more.

A Media3 session the device refuses to create costs the transport and never the cast: the service falls back to the plain ongoing notification and the serving socket behind it is unaffected. `CastNotificationPolicy` holds every decision above as pure JVM code and is unit-tested without a device, alongside `SeekPolicy.seekTarget`.

### Link capacity

Direct play never transcodes, so when the home Wi-Fi cannot carry a file's bitrate the cast dies of `startup_timeout` — a code that names the TV and implicates the file, when neither is at fault. Link capacity exists to put a correct face on that one failure. **It changes only sender protocol/runtime code: no capability, wire frame, or receiver runtime behavior changes.** Receiver launcher-resource changes in this visual refresh are unrelated. `net/LinkCapacityPolicy.kt` holds every threshold and every rule as pure JVM code; `net/LinkCapacityMonitor.kt` holds the state that policy needs and cannot keep. Both are unit-tested without a device.

**The measurement is sender-side, and that is what makes it sound.** The phone is the HTTP server, so it can measure the real path directly: `TransferTelemetry.recordBytes` sits on the socket write path in `MediaHttpServer`, and `CastServerService` folds it at 1 Hz into a `LinkSample` (bytes, elapsed, in-flight transfers). A server never writes faster than the client pulls, so an observed rate is a rate the path **demonstrably sustained**. The proof is therefore one-sided by construction: a fast reading can never be a false alarm, and the only thing the measurement can do is under-report a fast link — which it does routinely, because the TV stops pulling once its buffer is full. Every rule below is built around that asymmetry. `inFlight` is what separates the two directions of quiet: a link carrying nothing because nobody is asking is not a slow link, and any window containing an idle sample returns `Unknown` rather than a verdict.

The required rate is container bitrate — file bytes over container duration, because container bytes are what cross the wire. It is `null` outside a plausible band (100 kbps–400 Mbps), and a `null` is a permanent "say nothing", never a guess: MediaStore under-reporting duration on a long remux would otherwise manufacture a 500 Mbps requirement and libel a perfect link.

**`HEADROOM` is 1.25, and it is not the VBR peak ratio.** The tempting figure is peak-to-average — UHD Blu-ray runs 30–60 Mbps average against 128 Mbps peaks, i.e. 2.1x–4.3x — and anyone "fixing" this constant to 2.8x will start refusing casts that play perfectly. Content peaks are the **buffer's** job and the receiver's buffer is already sized for them: `BufferBudget.protectionSecondsAt` yields 39.5 s of cushion at 40 Mbps, 25.5 s at 60 and 14.3 s at 100, so a 2x excursion lasting 10 s costs 10 s against a 25 s reserve. Raising the headroom would be paying twice for the same peak. What 1.25 covers is measurement error and link variability, and nothing else.

Verdicts resolve in a fixed order, and the order is the design. A single sample at or above 1.25x real time returns `Proven` before any starvation test runs — that sample is proof the path carried the film, and no later throttling can unprove it. `Proven` is sticky across windows for the same reason: on a healthy link the buffer fills in seconds and throughput then drops to the *content* rate, which is exactly what a starvation test would misread. Only then: a window shorter than 6 s is a moment rather than a trend and returns `Unknown`; the first 2 s after the first byte are TCP slow start and the TV's opening range probes and are discarded; below 1.0x aggregate the buffer can only shrink, which is arithmetic rather than a heuristic, and returns `Starved`; between 1.0x and 1.25x returns `Marginal`, which is logged and **deliberately drives no UI anywhere in the app**.

**Nothing this feature introduces is terminal.** There is no pre-flight refusal and no gate. Before the first byte moves the phone knows only the negotiated Wi-Fi PHY rate, which over-reports usable throughput by 2–4x, so a gate built on it would refuse casts that work; the pre-cast card discounts PHY to 45% and is an advisory whose second button is the cast itself. Playback is never paused, stopped, sought or downgraded, quality is never reduced, and every card is dismissible. The only outcome that changes is a cast that was already going to fail.

`startup_timeout` is re-faced **locally, on the phone, with no wire change**. The coordinator freezes the verdict at the terminal into `failureLinkVerdict` (teardown resets the live monitor, so the error screen must not read the live one), and `castErrorFace` maps `startup_timeout` to `SLOW_LINK` instead of `SLOW_START` when that frozen verdict is `Starved`. Same wire code, same retry semantics, different copy — and the phone leads with "play on this phone", the one move that provably works. The stalling card during playback escalates on the rebuffer **count alone** (three in two minutes, excluding refills within 5 s of a seek or a subtitle reload, which cost one on any link); the verdict only chooses whether the copy quotes numbers, so a VBR-peak starvation the average-bitrate arithmetic cannot see still reaches the user, and a link that proved itself and stalled anyway gets a title that claims only the stalls rather than a bitrate verdict its own measurement contradicts.

## Receiver validation and playback

Before adopting media, `ControlServer` strictly validates `loadMedia` and the canonical URL: HTTP, port 8080, raw `/v/<22-character-token>`, authenticated numeric peer host, and no user-info/query/fragment/percent encoding. `loadAccepted` is the synchronous adoption boundary and duplicates replay the retained accepted/ready/failed result.

`PreflightProbe` has one absolute monotonic six-second deadline. It spends at most two seconds on a raw TCP connect, then at most three seconds per HTTP blocking phase while a scheduled disconnect enforces the absolute end. It sends `Range: bytes=0-1023`, disables redirects, requires 206 plus exact `Content-Range`/`Content-Length`, reads exactly the advertised bytes, and performs one EOF read. Drip-feed, early/extra body, 200, all 3xx, 4xx/5xx, and incoherent range data fail safely.

For playback, each Media3 `DataSpec` creates one `HttpURLConnection` with `instanceFollowRedirects=false`; every 3xx is rejected before any second request. The video codec selector filters software codecs and extension renderers are disabled. It filters on Media3's own `MediaCodecInfo.hardwareAccelerated`, which carries a usable verdict at **every** API level: on 29+ it is the platform's `isHardwareAccelerated()` flag, and below that Media3 derives it by naming the software/reference namespaces (`OMX.google.*`, `OMX.ffmpeg.*`, `OMX.SEC.*.sw.*`, `omx.qcom.video.decoder.hevcswvdec`, `c2.android.*`, `c2.google.*`, and anything outside `omx.`/`c2.` entirely, with `arc.*` excepted as hardware). `HardwareDecoderPolicy` mirrors that inversion as its fallback for a caller with no `MediaCodecInfo` to ask. An earlier `>= 29` gate discarded the pre-29 verdict and fell back to a MediaTek-only allow-list, which refused to play at all on the Amlogic, Realtek, Broadcom, Qualcomm and Samsung silicon that most of the API 26-28 Android TV installed base runs. An empty filtered list still deliberately makes Media3 report an unsupported video format rather than dropping to software.

The current cast/generation first-frame callback is installed before media/prepare. A single movable `PlayerSurface` stays attached to Media3 throughout Checking/Preparing behind an opaque Connecting overlay, then the same surface is revealed for Active playback; this preserves the real video output needed for the first-frame callback. Only `Player.Listener.onRenderedFirstFrame` transitions `Preparing` to `Active` and emits `loadReady`; `STATE_READY` alone is insufficient. The receiver's adoption-to-first-frame deadline is 18 seconds. Startup permits only two short transient-network retries (250 ms, then 500 ms) within that deadline; format/parser/decoder errors fail without entering the four-attempt steady-state recovery policy.

The budget answers exactly one question — can this link carry this file — and `StartupDeadlinePolicy` names the one thing it does not charge for. A picture-orientation re-prepare (see [Picture orientation](#picture-orientation)) — or the player swap that starts the effects graph, which is the same cost plus a decoder — is the receiver deciding on its own initiative to configure the decoder a second time; it discards the fill and re-fetches it, and charging that to the link would fail a sideways-filed film on a marginal link with `startup_timeout` — identically on every retry, because the automatic verdict recomputes the same, turning "the film looks sideways" into "the film will not cast". The grant is **6 seconds, at most once per cast**, sized on what the re-prepare has to buy back: `bufferForPlaybackMs`, which `BufferBudgetPolicy` caps at 2.5 s on every device tier, plus a codec teardown/configure and one byte-range round trip. That covers the re-fetch down to about half the file's bitrate, and a link delivering less than half cannot direct-play the file at all — so a genuinely slow link still fails, at 24 s rather than 18. A cast with no correction is untouched: same deadline, same timing, same failure. Extending re-arms the **timer**, not merely the timestamp `startPlayer` and `StartupRetryPolicy` read — a `delay(18_000)` job left running would otherwise still tear the cast down on the original schedule — and the grant is cleared with the rest of the startup transaction, so a re-target starts from a clean budget. `startupMs` is deliberately left alone: the real time to first frame from the single epoch is the honest number.

After first frame, the load-control tuning is **derived from the heap the process was actually granted**, not fixed. The previous fixed tuning was a live out-of-memory bug on the very device it was measured on, not merely an unportable one, and two facts about Media3 1.10.1's `DefaultLoadControl` are why (both read off the shipped AAR's bytecode):

- `shouldContinueLoading` compares against **`getTotalBufferBytesAllocated`** — every allocation the player holds. Retained back-buffer samples are allocated bytes, so `setBackBuffer` and the forward buffer spend **one** budget.
- Below `minBufferMs` it computes `isLoading = prioritizeTimeOverSizeThresholds || !targetBufferSizeReached`. With that flag set the byte target is ignored outright, so **no byte budget can bound the min-buffer allocation.**

Together: 30 s of back buffer plus a 15 s forward floor is 45 s of media resident whenever the byte target is reached first (rate ≥ ~47.7 Mbps), and 45 s is unbounded in rate — 429 MiB at 80 Mbps, **536 MiB at 100 Mbps against a 512 MB grant.** A genuine UHD remux could exhaust the heap; it survived only because the DV 8.1 test material sat lower.

`prioritizeTimeOverSizeThresholds` is therefore **false at every tier**. That is the correction that makes the byte target bind at every instant and every bitrate, and it costs nothing: below the planned peak the target is never reached before `minBufferMs` anyway. Turning it off also cannot wedge startup — `shouldStartPlayback` will start on the byte target being reached instead of on `bufferForPlaybackMs` of media, but only in the branch guarded by the flag being false, so the escape hatch exists exactly where the budget is tight enough to need it.

`bufferBudgetFor(Runtime.getRuntime().maxMemory())` takes 40% of the grant as the byte target, floored at 32 MiB and capped at **210239488 bytes (200.5 MiB) — Media3's own `DEFAULT_MAX_BUFFER_SIZE`**, the largest total the library will ever compute for itself. The old 256 MiB was above what Media3 considers safe, on hardware weaker than a phone. `maxMemory()` rather than `ActivityManager.memoryClass`/`largeMemoryClass` because `android:largeHeap="true"` is ignored on `isLowRamDevice()` hardware — exactly the class of TV at risk — and only `maxMemory()` reports the grant that happened rather than the one the manifest requested.

Durations follow from the budget, expressed as milliseconds *of 100 Mbps content* (`PLANNED_PEAK_BITRATE_BPS`, covering 4K remux VBR peaks). The forward buffer is allocated first because it is what rides out an outage; the back buffer takes a 15% share, capped at 10 s, and then only as much of it as genuine headroom allows. The whole configuration is **satisfiable** — `backBufferMs + minBufferMs <= plannedPeakFitMs` at every tier — which the previous one was not: it asked to hold 45 s inside a 21 s budget. The two playback thresholds are a **third** of the min buffer rather than merely capped by it, which is a second freeze closed: the sustainable cushion at bitrate *r* is `(target - backBytes) / r`, which equals `minBufferMs` exactly at the planned peak and is *smaller above it*, so a resume threshold equal to the min buffer leaves the player permanently at the level it resumes from — and above the peak the cushion falls under the threshold and playback can never resume at all. A third keeps the cushion at 3x the resume threshold at the peak and 8x at 40 Mbps, and pushes the point where the cushion drops under it out to ~231 Mbps, past UHD Blu-ray's 128 Mbps ceiling. On a device that can only hold 2.7 s, waiting 5 s to resume would mean never resuming. At a 512 MB grant: 200.5 MiB target, 14.3 s min buffer, 2.5 s back buffer, 2.5 s initial and 4.8 s post-rebuffer thresholds. At 256/128/96 MB: 102.4/51.2/38.4 MiB target, 7.3/3.7/2.7 s min buffer, 1.3/0.6/0.5 s back buffer and 2.4/1.2/0.9 s post-rebuffer thresholds. Unchanged around it: 180 s `maxBufferMs` as a ceiling that only binds below ~9.3 Mbps, up to 20 load retries with five-second capped backoff, and four bounded fatal-transient recovery attempts at 2/4/8/15 seconds. The budget and its ride-out are logged at player construction.

The back buffer is small deliberately, and 30 s was the second half of the bug. Back-buffer retention is **passive** — not gated by the byte target — so it does not merely compete with the forward buffer, it crowds it out: let it reach the whole target and `targetBufferSizeReached` is permanently true, forward loading never resumes, and the player rebuffers forever with no error raised. A 15% share keeps that impossible up to ~667 Mbps. The 10 s ceiling deliberately does not try to serve the 10 s `seekBack` from memory: that would cost 125 MiB at the planned peak, 60% of the budget, paid out of outage protection. What it does buy is `retainBackBufferFromKeyframe` re-anchoring a step back inside the current GOP.

**Ride-out is `BufferBudget.protectionSecondsAt(bitrate)` and nothing else** — the forward buffer at the file's own bitrate, with the back buffer's share deducted. At a 512 MB grant that is 39.5 s at 40 Mbps, 25.5 s at 60, 18.5 s at 80 and 14.3 s at 100. There was no 180-second property to preserve: `MAX_BUFFER_MS = 180_000` was reachable only below ~10 Mbps, so at 60 Mbps the receiver rode out 15 s and the ~70 s wireless outage the old comment cited as the *reason* for the tuning would have stalled anyway. The new numbers are strictly better on both axes — longer ride-out at every real 4K bitrate, and resident memory hard-bounded at 200.5 MiB instead of unbounded.

An unplayable video no longer waits out the startup deadline. When the codec selector hands back an empty list the track selector marks the video `FORMAT_UNSUPPORTED_SUBTYPE` and simply **does not select it** — so no `PlaybackException` is raised at all, the audio track plays on over a black screen, and the only thing that eventually fires is the 18-second deadline reporting `STARTUP_TIMEOUT` with `retryable = true`: "didn't start in time" plus a Retry that can never succeed. `videoTrackShortfall` reads the selection instead. A video group present with nothing selected is the signal; the **best** support level across the group decides the reason (a best of `FORMAT_HANDLED` returns null, because something other than capability declined to select it and refusing there would refuse a playable film). `PlayerController` raises `UnplayableVideoTrackException` through the existing error path, skipping the transient recovery budget outright — no amount of re-preparing gives a TV a decoder it does not have.

That is what finally emits `unsupported_video_codec` and `unsupported_hdr_profile`, both of which were already in the v2 vocabulary with sender-side copy and were previously never produced by anything. No wire change is involved. Dolby Vision is separated from the generic codec answer because `video/dolby-vision` as an unsupported subtype means precisely that the TV has no DV pipeline; an `EXCEEDS_CAPABILITIES` verdict stays generic, because a 4K DV file rejected by a 1080p decoder is a resolution fault and blaming HDR would be inventing a cause. `ERROR_CODE_DECODER_QUERY_FAILED`, `ERROR_CODE_DECODING_RESOURCES_RECLAIMED` and the four `AUDIO_TRACK_*` codes now map to `DECODER_INIT` rather than `UNKNOWN` (the vocabulary has no audio-specific code and adding one would need a matched release of both apps), and `ERROR_CODE_DECODING_FAILED` maps to `MALFORMED_MEDIA` — a decoder that accepted the format and then failed on samples is reporting the bitstream, not the TV.

`ErrorKind` has a third value. Everything that was not `Unreachable` used to collapse to `NotServing`, which put *"Your phone stopped serving… battery saver paused it"* on the TV screen for a decoder failure, blaming a phone that was serving perfectly. `errorKindFor` routes the media/decode verdicts — malformed, unsupported container/format/codec/HDR profile, and `DECODER_INIT` — to `ErrorKind.Unplayable`, whose copy lives in `res/values/strings_playback.xml` and never blames the phone or offers a retry.

Decoder fallback is **on**. It does not weaken the hardware-only claim: the selector has already removed every software decoder from the candidate list and fallback can only walk to the next entry of that list, so there is nothing software left to fall back to. What it buys is the retry to a second *hardware* decoder on a TV that ships more than one.

### A/V sync nudge (audio delay)

The remote's middle segment adjusts audio against picture for the running cast. **What the receiver actually moves is the picture**, and that is the whole design rather than an implementation detail. Media3 1.10.1 exposes no audio-offset API — `AudioSink.setOutputStreamOffsetUs` is a gapless-transition hook, not a sync control — and the only offset a player could grow on the audio side is an `AudioProcessor` padding or dropping PCM, which `DefaultAudioSink` bypasses entirely when encoded audio is passed through to the HDMI sink. That is exactly the E-AC3 / DTS / TrueHD content this product exists to direct-play, so an audio-side implementation would have silently done nothing for the files most likely to need it. Advancing the picture by the same amount is indistinguishable to a viewer and touches the audio path not at all.

`FlickRenderersFactory` — the receiver's single renderers factory, described in full under [Picture orientation](#picture-orientation) — wraps every `C.TRACK_TYPE_VIDEO` renderer `createRenderers` produced in an `AudioDelayVideoRenderer`, a `ForwardingRenderer` that adds a µs shift to `render(positionUs, …)` and to `getDurationToProgressUs`. The offset is one `@Volatile` field on an `AudioDelayShift` owned by `PlayerController` and handed to the factory, so unlike `lastVolume` there is nothing to re-apply after a background/foreground rebuild — the replacement renderers read the same instance. Nothing is pushed into the player, so there is no re-prepare, no seek and no re-buffer. **The media clock is untouched**: it belongs to the audio renderer, so reported position, the scrub bar, the `state` frames and the resume checkpoints all stay exactly as honest as they were.

The wire is one new command, `setAudioDelay {t,v,castId,delayMs}`, specified in [control-channel.md](design/control-channel.md); the capability list gained a fifth entry, `audio-delay`, which changes the pairing HMAC transcript and is why the fixtures were regenerated. A positive `delayMs` is audio heard **later** than the picture — VLC's and mpv's convention — and nothing in either app prints the offset without also stating the direction in words, because the sign alone reads either way round to most people. The range is ±5000 ms on a 25 ms grid; the receiver **refuses** anything outside it rather than clamping, so a widened sender is a frame the TV drops on the floor and the two move together or not at all. What the receiver does clamp is what it can actually *render*: five seconds of forward buffer is 62.5 MB of 100 Mbps content, which fits the 14,297 ms a 512 MB heap grant buys and does not fit the 2,282 ms of `BufferBudgetPolicy`'s smallest tier, so the applied shift is capped against the budget that device was built with and logged beside the commanded one. Legality is a wire rule and is device-independent; renderability is not, and confusing the two would let a small heap kill the control socket. The value is per cast and lives on the phone: no `state` frame carries it and the TV never reports it back, so both sides independently drop it to zero on a genuinely new cast and neither touches it for anything else. The receiver's reset is the single line in `SessionController.onLoadMedia` after the replay-result early return — control ownership routes a repeat `castId` to `onReloadMedia`, so a subtitle swap, a startup retry, a seek and a player rebuild all keep the nudge the viewer dialled in.

**The phone remembers the offset per film and puts it back**, which is the one thing that survives that reset — and only on the phone: the wire, the receiver and the per-cast reset are all unchanged. `media/AudioDelayMemory.kt` keeps up to 100 records in a **second** Preferences DataStore, `flick_audio_delay`, keyed by `PlaybackMediaFingerprint` — literally the identity the resume checkpoint is filed under, so one film has one identity and a re-encode costs the nudge exactly as it costs the resume position. It is a separate file from the checkpoints because Preferences DataStore rewrites the whole file per edit and serialises those edits, so sharing one would make each writer wait behind the other and would put both features behind one corrupt file. Records are `"<delayMs>:<updatedAtEpochMs>"`, pruned oldest-settled-first at the hundredth, and **validated rather than repaired on read**: a value out of range, off the 25 ms grid, or equal to in-sync is treated as absent, because a bound the viewer never chose silently in force on a film is worse than no memory. In-sync is stored as the *absence* of a record — dialling the nudge back out removes it — so a film that needs no offset leaves no trace and the hundred records are spent on the films that do. Writes are debounced by `AudioDelayMemoryPolicy.SETTLE_QUIET_MS` (400 ms, ten walk hops) through `collectSettledAudioDelay`, so a drag and a 40-hop walk each cost one write for the value the viewer stopped on rather than 25 a second for values they passed through; every value restarts the window, so what it has to outlast is one hop and not the whole 1.56 s walk, and the cast's own teardown flushes whatever the window did not. The `AudioDelayRecorder` mirrors the checkpoint recorder exactly — one write in flight per cast, acknowledged exactly once through the same `drainStoreWrites` loop, a failed write re-offered rather than assumed. On a new cast, `startCast` reads the memory without waiting (the store starts reading at launch and fails open to `Ready`; a cast is not held up for a decoration) and applies it **after** `loadMedia`, which is what resets both ends to zero, as a **single frame** through `PlaybackSession.applyRememberedAudioDelay` rather than a walk: the walk exists to protect a picture already on screen from the drop-to-keyframe branch, and a cast that has decoded nothing yet has no such picture. The recorder is armed with that same value as already-durable, so watching a film at the offset it was left at rewrites nothing. The store is excluded from backup and device transfer for the checkpoints' reason: its hashed keys name MediaStore revisions that exist only on this phone.

The nudge is instrumented as **two halves of one claim**, for the same reason rotation is: no frame carries the value back, so "the phone sent it" and "the picture moved" are separate facts. `[player] audioDelay ms=75` is written on the main thread before the player is touched at all, and says only that a frame arrived and was accepted. `[player] audioDelayShift us=75000` is written from the thread that releases frames, by the renderer that is actually in the array — so the two together separate a command the TV took from a command that reached the picture, and the second appearing under a `ForwardingRenderer` that was never wrapped is the failure it exists to catch. It compares and returns on every other tick; a viewer stepping the value changes it a few times a second at most. The two `command drop` lines listed under [Picture orientation](#picture-orientation) cover `setAudioDelay` too.

**The steady state is free in both directions; a discontinuity is not, and there are two of them.** Media3 holds a frame that lands more than 50 ms early, drops one more than 30 ms late, and past 500 ms late abandons decoded buffers forward to the next keyframe — a visible skip that takes a GOP to recover. So a *change* of shift is paid for once by the picture in proportion to the size of the change, and, less obviously, **every seek at a non-zero delay re-pays it**: after a seek to P the decoder can only supply frames from P while the shifted clock already sits at P±D, so a scrub or a ±10 s tap costs roughly |delay| of dropped frames catching up, or of held picture, depending on the sign. Both are bounded by |delay| and self-correcting, and neither is fixable within this approach — a renderer cannot show frames it does not have. At the far end of the range that seek cost is the whole five seconds, and it is the price of the range rather than a defect in it. It is also why the phone never puts a large jump on the wire: `AudioDelayPolicy.approach` caps any single frame at 250 ms of picture — exactly half the keyframe branch — and `PlaybackSession` walks anything larger as a run of absolute values at 40 ms a hop, so a bound-to-bound slam, a blade tap on the far end of the track, a screen reader setting the value outright and a Reset from a bound all land in 40 hops over 1.56 s at 25 frames a second, which is the rate the channel is already sized for under a scrub. The text renderer is deliberately **not** wrapped, so subtitles stay on the unshifted audio clock and drift against the picture by up to the delay; subtitles transcribe dialogue, so tracking the audio is the right side to be on.

The receiver's committed profile has since caught up: `FlickRenderersFactory`, `AudioDelayVideoRenderer` and `RotationCorrectingVideoRenderer` all appear in both `baseline-prof.txt` and `startup-prof.txt`, as does the sender's `VideoTile`. The residual gap is now on the phone's notification path — `CastMediaNotification`, `CastRemotePlayer` and `CastArtworkCrop` are in neither sender profile, so the first artwork decode and the first notification post run interpreted on `release` until `:sender:generateReleaseBaselineProfile` is re-run with a phone attached. `release` still assembles and still packages the profile already committed; generation is never part of `assemble*` (`automaticGenerationDuringBuild = false`), so a stale profile costs startup AOT coverage, not a build.

`SubtitleTooLargeException` is in the load-error fail-fast set alongside `RedirectRejectedException`. It is not an HTTP verdict but it is just as final — the body has already exceeded the cap, so every retry re-fetches the same oversized file. Media3 routes the subtitle `SingleSampleMediaSource` through the same load policy as the film, so the receiver first preserves those fatal classifications, then gives other text-track failures only one 250 ms retry. The 20-attempt capped LAN policy remains exclusive to non-text media loads.

Panel capability is recorded, never enforced. `DisplayCapabilityPolicy` compares the decoded format against the display's advertised HDR types and its physical mode and logs any shortfall (`panelShortfall hdr:DolbyVision`, `downscaled:3840x2160`) when the video input format becomes known. It does not refuse playback: there is no transcode and no downscale here, so the only alternative to presenting the film anyway is refusing it, and `Display.HdrCapabilities` is under-reported often enough on Android TV that refusing on it would break films that play correctly today. An empty HDR-type list is read as unknown rather than as a shortfall for the same reason. This is separate from the decoder question above, which is enforced.

Refresh-rate matching is **derived state, never a latch**. `preferredWindowRefreshRate(presentingVideo, contentFrameRate)` is the single decision: while the player surface is actually presenting a film and the decoder reports a real cadence, that cadence is applied to both `WindowManager.LayoutParams.preferredRefreshRate` and `Surface.setFrameRate` (`FIXED_SOURCE`, `CHANGE_FRAME_RATE_ALWAYS`), which is what removes 3:2 judder on 23.976/24/25 fps material. In every other state — pairing, idle, settings, an error, and any frame rate that is 0/NaN/infinite — both hints are released by re-applying the platform's `0` sentinel, and the release also runs when the receiver composable leaves composition. The one state that neither pins nor releases at once is the **handshake**: a cast arriving over a running film — the next episode — passes through Checking/Preparing while the old film is still decoding under the connecting cover, so `refreshRateHintDelayMs` defers a release by a 2-second settle there. A subtitle change no longer reaches that settle at all: an in-place reload never leaves `Active`, so the hint is simply never released, which is the correct answer for a re-prepare of the very same film. Probe plus prepare on a LAN file lands far inside it, and the ordinary re-cast therefore costs zero mode switches instead of a release and an immediate re-pin at the same cadence — two visible HDMI resyncs for a hint that never changed. It is a settle rather than a hold because the adoption deadline is 18 seconds and a stalled handshake may not keep the panel pinned to a finished film. The previous one-way apply was guarded by `if (fps > 0)`, so when playback ended and the reported frame rate fell to 0 the branch was skipped and the film's hint survived it: the TV was measured sitting on the **pairing** screen with `preferredRefreshRate=24.000002` and a 41.67 ms vsync period, rendering every spring, fade and focus lift in the whole Compose UI in 24 discrete steps a second, for the rest of the process. The rate is deliberately **not** released for interactive chrome over a running film: a display-mode switch on the verified hardware costs a visible resync, and two of them per chrome reveal is worse than chrome animating at the film's own cadence.

Playback chrome is a glass transport panel anchored inside the 5% TV-safe inset, not a full-width bottom bar: the media title is a single ellipsized 34sp line, timecode is 20sp tabular mono, transport targets are 52dp/66dp with 26dp/35dp seek and play glyphs, and the movie frame stays visible behind lighter pause/seek/buffering dimming. The top and bottom scrims are gradients that fade in and out with the chrome rather than permanently overlaying the film. Focus is a detached amber ring drawn outside the element bounds, so focusing a control never reflows its row; the play key takes the white ring because amber on amber would vanish, and the scrub bar draws its ring around the knob rather than around a 700dp span. **The control row is traversed the way it is drawn**: left/right step through `subtitles → back-10 → play → forward-10 → volume → stream metrics`, up from any of them reaches the scrub bar, down from the scrub bar returns to the row, and up from the scrub bar reaches `END SESSION`. Revealing the chrome still lands focus on play; after a side panel closes it lands on the card that opened it. Because both handoffs compose the arriving surface in the same frame that removes the departing one, entry focus is requested across several frames (`landTvFocus`) rather than once — a `FocusRequester` whose node has not been placed yet throws, and there would be nothing else on screen to steer with.

Only **FINISHED** still draws a centred state chip. The paused chip was cut: a viewer who has just pressed pause is being told what they did themselves, over the frame they paused to look at. Paused instead auto-hides the chrome on the same 4-second countdown as playing, and leaves the amber play key resting at the foot of the frame. That key is a state signal, not a control — not focusable, no click action, and DPAD center/up/down restore the full chrome. Left and right stay the blind seek they are under any hidden chrome: the paused-rest state does not get its own key model, and a paused film is exactly when stepping through it without a panel in the way is wanted. Its bright amber gradient carries **80% opacity**, its ink stays solid, and it reuses the primary key's small amber shadow. An explicit top sibling z-index keeps the state signal above Media3 subtitles and every playback overlay without adding a full-screen layer or per-frame effect.

Three side panels **replace** the transport bar rather than stacking on it, and are the only chrome that suspends the 4-second auto-hide: **Subtitles** lists Media3's live text tracks with the format its sample MIME actually names, plus the Small/Medium/Large caption size; **Orientation** carries the picture-orientation cells described under [Picture orientation](#picture-orientation); **Stream metrics** shows a 40-bar throughput histogram over the rolling peak and a nine-cell stat grid. Subtitle focus follows an explicit `Off → live tracks → selected size` chain, with the size row the final rank that Down cannot leave through; a live track refresh preserves the focused logical track when it survives and otherwise re-lands on the current selection or Off, and focus resting on a size cell is never moved by a track appearing or disappearing around it. All three panels read only measured fields — an unavailable value renders as an em-dash or is omitted, never as a plausible number, so file size and any synthesized countdown are absent by construction. The panel is a sibling of the transport in the layout, not a child of it, which is what lets it outlive the bar; opening one hides the bar, closing one brings it back with focus on the card that summoned it, and Back dismisses the panel before it can hide the chrome or end the cast. The countdown stays suspended while a panel is open precisely because the bar is gone — firing it would take away the surface the viewer expects to return to. The opt-in `Playback metrics overlay` dev HUD from Settings paints only while the chrome is hidden, because the redesigned chrome owns the corners it used to occupy.

Resolution is classified in exactly one place, `videoResolutionClass(width, height)`, shared by the transport's spec chip and the start-of-cast quality card. It reads the frame's **long edge**, not its height: a 2.39:1 feature is encoded 1920×804 with the letterbox baked out, so a height-only ladder found 804, cleared the 720 rung and labelled every scope film on the drive "720p SDR" while the phone, reading the same file, said 1080p. The short edge is kept as a second test so portrait and rotated capture — 720×1280 — is still read by the dimension that carries its scale.

Media3 **text** subtitles retain their viewport-derived/user-scaled baseline minus exactly 2sp, then multiply it by the panel's caption-size choice (0.85 / 1.0 / 1.25, floored at 1sp); the platform caption-manager scale still governs the baseline and the existing caption/layout/configuration listeners are unchanged. They use white text with a drop shadow, and ignore embedded cue styling/font sizes that would override this treatment. Because embedded styles are disabled, the cue typeface is set explicitly to the bundled Geist SemiBold `res/font` face rather than left null: a null typeface renders cues in the platform default (Roboto Regular 400), below the receiver's ten-foot weight floor and in a different family from the rest of the UI. The per-glyph background is fully transparent; a single 55%-opaque black Media3 cue window supplies the visibly translucent plate without overlapping glyph/run backgrounds becoming effectively opaque. Disabling embedded styles clears source cue-window overrides, so Media3 falls back to this `CaptionStyleCompat.windowColor`. Caption font-scale changes are applied in place without recreating the Activity or tearing down the cast. Bitmap subtitle cues (for example PGS/VobSub) have styling baked into their pixels, so Media3 renders them unchanged as the non-destructive fallback; the metrics overlay reports selected subtitle MIME plus `text`/`bitmap`/`mixed` cue shape without retaining cue text or bitmap payloads.

Android TV remote input is routed first at `Activity.dispatchKeyEvent`, independent of Compose focus. During Active playback with no side panel open, DPAD left/right are a **playback gesture in exactly two states** — the chrome is hidden, or the scrub bar itself holds focus — and are ordinary Compose focus navigation everywhere else. That is the corrected model: while horizontal keys were captured unconditionally, a transport row laid out horizontally could only be walked with up and down, which is what the product owner rejected on the device. A tap seeks exactly ten seconds; a held key emits every fourth repeat and progresses through capped 10/20/30-second pulses (1×/2×/3×). While playback gestures are enabled, the Activity consumes the full gesture through key-up, and the captured gesture outranks both chrome visibility and scrub focus, so a chrome auto-hide or a focus move landing mid-hold cannot split one physical press into two meanings. It outranks the other DPAD keys too: while a gesture is held, a second direction — a thumb rocking the ring — is swallowed rather than allowed to take the capture, because the held key's key-up would then match nothing and the gesture would never end. The burst state is derived from the capture rather than credited to whichever key released one, so no path can leave it frozen over the film; and because only the holder's own key-up releases it during playback, a capture that outlives its release (a window-focus loss swallows the key-up) is cleared by pressing that same direction again rather than by a different one. Dedicated media keys are excluded from all of this and keep falling through. A burst on the seeked half of the frame shows the gesture's accumulated signed delta and acceleration, holds for 700 ms after release, then fades and clears; it is shown only for a **blind** seek, because with the chrome up the scrub bar is already drawing the target, the ghost and both timecodes. A blind seek deliberately does **not** summon the chrome — quick-seek without bringing up UI is the TV-player convention, and revealing it would make the second tap of a double-tap a focus move rather than another ten seconds. With chrome hidden, DPAD center/Enter toggles play-pause once per press and up/down reveal the chrome; with chrome visible those non-horizontal keys fall through to the transport focus graph. An open side panel hands the whole DPAD to Compose: the receiver reports `playbackActive = false` to the policy, which clears any stale playback capture and passes the event through unconsumed. There is no longer a volume-engagement latch at the Activity boundary — volume reads left/right through its own key handler while it holds focus, and horizontal keys can only bypass Compose when the scrub bar holds focus, so the two can no longer claim the same key. Dedicated play, pause, play-pause, rewind, and fast-forward buttons are never consumed by the Activity policy: Android delivers them to a Media3 `MediaSession`, whose ten-second seek increments match the on-screen transport. Media Stop and unsupported Next/Previous are consumed/rejected by the session callback because raw `Player.stop()` or playlist navigation would bypass cast ownership and terminal-state bookkeeping. The platform session switches to a replacement ExoPlayer before the prior instance is released, is released before decoder teardown or terminal cast stop, and is rebound before any later playback. Outside Active playback custom DPAD keys fall through to normal Compose/system navigation.

### Picture orientation

Some landscape films are filed sideways and play as a tall strip on the TV. That is not a layout fault: ExoPlayer is faithfully honouring `Format.rotationDegrees` from the container's display matrix, and the metadata is simply wrong. Confirmed against the shipped media3 1.10.1 bytecode — `MediaCodecVideoRenderer.getMediaFormat` copies `rotationDegrees` into `MediaFormat.KEY_ROTATION`, and `onOutputFormatChanged` unconditionally swaps width/height and inverts the sample aspect for a 90/270 turn while building a three-argument `VideoSize`, so the **decoder** applies the rotation while rendering to the surface and `unappliedRotationDegrees` is always 0.

The cheap half of the fix rewrites the one number the decoder is configured with, and nothing else. `RotationCorrectingVideoRenderer` overrides `onInputFormatChanged` and rebuilds `formatHolder.format` with a corrected `rotationDegrees` — the same seam media3 itself uses in `BaseRenderer.readSource`. Where the display pipeline honours it that is as cheap as today's behaviour for the same content, because it *is* today's path: no `setVideoEffects`, no GL pass, and no `TextureView`. The hardware overlay, tunneling, Dolby Vision, HDR and the tuned `DefaultLoadControl` are untouched. It is still the only mechanism used when the picture does not have to move.

**On the verified hardware it is not enough, and that was confirmed on the device rather than deduced.** `KEY_ROTATION` is not a decoder feature: the platform turns it into a buffer transform on the codec's output surface (`SurfaceUtils::setNativeWindowRotation` → `native_window_set_buffers_transform`), and the display pipeline is expected to apply it while compositing the video layer. The Google TV Streamer's does not. Every software hop succeeded and the picture still did not turn — `rotation choice=Quarter extraDegrees=90 rePrepared=true`, then `rotationToDecoder container=0 decoder=90 … applied=90`, then `videoSize w=1080 h=1920` — because media3 transposes the reported size from `Format.rotationDegrees` on its own assumption that the transform landed. The result is a picture whose BOX turns while the pixels inside it stay flat, letterboxed into a portrait window. Google's Android TV team has said of the same failure on other panels that it "cannot be fixed retroactively" ([google/ExoPlayer#11038](https://github.com/google/ExoPlayer/issues/11038)); media3's own answer there is `ExoPlayer.setVideoEffects`.

**So a turn that has to actually happen is carried by media3's effects graph, and only then.** `PlayerController` calls `ExoPlayer.setVideoEffects` with a single `ScaleAndRotateTransformation`; the codec's output surface becomes a `SurfaceTexture`, the turn happens in a vertex shader, and `FinalShaderProgramWrapper` renders the result to the same `SurfaceView` — no `TextureView`, so the HDR path, DRM output and the TV's full-resolution video layer are all still on the table. `androidx.media3:media3-effect:1.10.1` is a new dependency and a required one: `media3-exoplayer` reaches it only by reflection (`PlaybackVideoGraphWrapper` → `androidx.media3.effect.SingleInputVideoGraph`), does not depend on it, and `setVideoEffects` throws `IllegalStateException` without it.

`pictureTurnFor` in `player/PictureTurnPolicy.kt` is the whole decision, pure and unit-tested. **The gate is the TOTAL turn, not Flick's share of it**, and the two cases that separates are the point. A total of zero — every ordinary cast, *and* an Auto correction where the container's 90 and Flick's 270 cancel — reaches the decoder as rotation 0, which is not a transform at all, so no display pipeline can fail to honour it and no graph is ever built. **An untouched 4K Dolby Vision cast is therefore byte-identical to having no rotation feature.** A non-zero total means a transform has to happen somewhere, and the graph takes it: the decoder is then given **0** rather than the total, both because two mechanisms applying the same turn would land 180 out on hardware where the codec's transform does work, and because a zero keeps media3's reported `VideoSize` equal to the coded size — which is also the size the graph is registered with and the size of the frames that arrive, so the whole chain agrees and the shader fits the turned frame into the surface itself. `Format.rotationDegrees` is clockwise and `ScaleAndRotateTransformation` is counterclockwise; `PictureTurn.frameDegreesCounterClockwise` is the only place that knows it.

**The turn is resolved once per film, as soon as the tracks are known — not only when Auto changes its mind.** That distinction was a real bug and it is worth naming, because the case it broke is the commonest one there is. A video shot on a phone is stored as a landscape coded frame with a 90° display matrix, and `autoRotation` deliberately answers `LooksLikeACameraClip` with **0** extra degrees for it — correctly, because the container is right and Flick must not overrule it. But the resolution used to be reached only when Auto's answer *differed from the previous film's*, and 0 never differs from the 0 a reset leaves behind. So `pictureTurnFor` was never asked, the graph was never built, and the decoder was configured with the container's own 90 — which this TV drops. Every clip the user had ever shot played sideways from the first frame, with no key pressed and nothing in the log to say why. Resolving unconditionally on the first delivery fixes it, and the total-turn gate is what keeps that free: a film whose container declares nothing still resolves to a total of zero, still builds no graph, and still issues no re-prepare. What it does change is that a container-rotated film now earns its graph during startup rather than never, which costs it one player swap before the first frame and a GL pass per frame afterwards — the price of the picture being the right way up on this panel.

**What a turn costs, stated rather than hidden.** The graph is not free, and on this panel it is not lossless either. Read off the device: the Google TV Streamer is `Imagination PowerVR Rogue GE9215`, OpenGL ES 3.2, with `GL_EXT_YUV_target` — everything media3 needs to *read* HDR — and its EGL advertises **neither** `EGL_EXT_gl_colorspace_bt2020_pq` nor `EGL_EXT_gl_colorspace_bt2020_hlg`, which is what it would need to *present* it. `PlaybackVideoGraphWrapper.registerInput` does not fail on that; it logs "Color transfer … is not supported" and falls back to OpenGL tone mapping. So:

- **SDR** — turned, at no cost to the picture.
- **HDR10 / HLG** — turned, and shown in SDR for as long as the turn is in force. `GlColourOutput` queries the two EGL extensions once and reproduces media3's own rule (`hdrSurvivesFrameProcessing`), so a TV that *can* present BT.2020 keeps its grade and is told nothing.
- **Dolby Vision** — never enters the graph. `GlUtil.createEglSurface` accepts SDR, BT.2020 PQ and BT.2020 HLG and nothing else, so there is no surface a DV RPU can be presented through, and 4K DV plus effects is a reported decoder-init failure on this SoC family ([androidx/media#1630](https://github.com/androidx/media/issues/1630)). The turn stays with the decoder, which on this TV means the picture does not move.

The last two are the reason the panel has a note. `TurnNote.ShownInSdr` and `TurnNote.NotOnThisTv` replace the `AUTO · 90°` eyebrow in the orientation panel for as long as there is something to say — *TURNED · SHOWN IN SDR* and *THIS TV CAN'T TURN THIS FILM* — because what a turn could not do to the picture is legible from nowhere else, while what Auto settled on is already legible from the selected row. A refusal is never silent.

**The graph is a property of the player instance, not of the film,** and that is what decides the cost of changing a turn. media3 builds it while a video renderer is first enabled (`MediaCodecVideoRenderer.onEnabled`, guarded by `hasSetVideoSink`, which only `onReset` clears) and `videoEffects` can never be set back to null — so `setVideoEffects` has to be called before the instance's first `prepare()`, and **starting or stopping the graph is a new ExoPlayer instance**. `rebuildPlayerForTurn` performs that swap where the film already is, modelled on `playStartup`'s: URL, position, sideloaded subtitle, media id, platform session, volume and instrumentation all survive, the new instance is published to Compose before the old one is released so `setKeepContentOnPlayerReset` holds the last frame across the gap, and it costs a re-buffer plus a decoder. **Changing the turn inside a graph that already exists costs nothing at all** — `PlaybackVideoGraphWrapper.setVideoEffects` re-registers the input stream with the new effect list, the codec stays configured at 0 whatever the turn is, and the picture turns on the next frame without the film stopping.

**A turn must never cost the viewer the film**, and the hard part is that a graph can fail without raising anything. Four routes reach one `failFrameTurn`, which latches the film as graph-unavailable, rebuilds without the graph at the last good position, and shows *THIS TV CAN'T TURN THIS FILM* instead of ending the cast on a diagnosis screen:

- **A raised playback error** — `ERROR_CODE_VIDEO_FRAME_PROCESSING_FAILED`, `…_PROCESSOR_INIT_FAILED`, or a decoder that will not configure against a `SurfaceTexture`.
- **`setVideoEffects` throwing synchronously.** It reflects on `androidx.media3.effect.SingleInputVideoGraph$Factory` before sending the renderer message and throws `IllegalStateException` if lib-effect is not reachable, so both call sites fail closed rather than letting it escape a control-command handler.
- **A track the selector will not play once the graph is in the way.** `reportUnplayableVideoTrack` synthesises its own error and never passes through `onPlayerError`, so it used to reach the diagnosis screen with no fallback at all. It now routes here first, before the shortfall verdict is latched, so the no-graph player is judged on its own tracks.
- **`FrameTurnWatchdog`** — the case with no error to catch. A newly engaged graph that renders no frame inside 12 s is condemned. The frame signal is `setVideoFrameMetadataListener` rather than `onRenderedFirstFrame`, because media3 resets no first-frame state when a *live* graph is handed a new effect list and the callback would never fire again. That signal has its own trap: `setVideoEffects` is an asynchronous renderer message, so frames already inside the GL pipeline drain under the **old** list and would clear a deadline armed for the new one. Frames therefore only count as evidence 1.5 s after a live swap — a 6× margin over the ~6 frames media3 can have in flight (`getMaxPendingFramesCountForMediaCodecDecoders` is 5, plus `FinalShaderProgramWrapper`'s single surface-input slot). The window never shortens the deadline; it only refuses early frames as proof, so it cannot condemn a graph that works. `STATE_ENDED` is excused — a finished film renders nothing forever — while `STATE_BUFFERING` deliberately is not, because a wedged graph and a genuine rebuffer leave the renderer in the same state and excusing it would excuse the failure being watched for.

The hand-back gets its **own** `PendingWork` slot rather than sharing `pendingRecovery`: an error already queued on the main thread would otherwise run first, see the latch, schedule an ordinary recovery, and cancel the hand-back on its way — leaving the film condemned, the graph still installed and the fallback never run. Errors raised in that one main-thread turn are absorbed, because the hand-back is itself a full re-prepare and the error belongs to the graph being abandoned. The verdict is remembered for the film's URL in a bounded, session-only `FilmsWithoutFrames`, so the receiver's own startup-retry ladder cannot re-engage a graph that has already proved dead and fail identically every time; a phone-initiated re-cast mints a fresh token and does get one more attempt, caught by one more deadline. A second failure takes the ordinary route, which is what keeps this from swallowing a genuine decoder shortfall.

**Mechanisms rejected, and why.** `View.setRotation` on the `SurfaceView` — AOSP's `SurfaceView.onSetSurfacePositionAndScale` passes position and axis-aligned scale to the layer and hardcodes the two skew terms to `0f`, so rotation is not representable; the documented guarantee covers "translating and scaling" only. Rotating a parent `ViewGroup` — identical code path, so the box rotates and the buffer does not. A transform on `SurfaceView.getSurfaceControl()` — the javadoc states it is "effectively read-only" and that the SurfaceView "may mutate" its properties "at any time", `Transaction.setMatrix` is `@hide`, and the returned control is a bufferless container layer. `TextureView` — it does rotate, and it costs HDR unconditionally (Android 13+ tone-maps `TextureView` HDR to SDR by platform design), plus DRM output, tunneling, up to 30% more power, and — decisively for this product — the ability to render at the display's full resolution on an Android TV box that upscales its UI layer.

**One factory carries both video customisations**, because ExoPlayer accepts exactly one and orientation and the [A/V sync nudge](#av-sync-nudge-audio-delay) both customise the video renderer. `FlickRenderersFactory` composes them by hooking two different levels of `DefaultRenderersFactory`: `buildVideoRenderers` **constructs** the rotation-aware renderer, and `createRenderers` — which is what calls it, so `super` runs that override — then **wraps** the result in the audio-delay shift. Rotation lands in the decoder's configuration and is settled once; the shift lands in the frame-release decision and moves live. Neither can observe the other, and with no rotation asserted and a zero delay the factory builds what `DefaultRenderersFactory` builds.

Overriding `buildVideoRenderers` costs less than it appears to, and the trade-off is worth stating exactly. The hardware-only `MediaCodecSelector` and the decoder-fallback flag are **parameters** of that method — media3 reads them off its own fields in `createRenderers` and hands them down — so forwarding them loses nothing the caller configured. What is genuinely forfeited is the four settings media3 1.10.1 forwards from factory fields the parameter list does not carry: `parseAv1SampleDependencies`, `lateThresholdToDropDecoderInputUs`, `setEnableDurationToProgressUs`, and on API 34+ the buffer-decode-only flag. This module sets none of them, and each factory default was checked against the shipped bytecode to be the value `MediaCodecVideoRenderer.Builder` already defaults to on its own (`true`, 15000 µs, `false`, `false`), so reproducing them would change nothing today. The real forfeit is future construction logic added there, which reaches this renderer only when someone updates the chain. The extension-renderer branch is dropped rather than reproduced, because the receiver pins `EXTENSION_RENDERER_MODE_OFF`.

`createSecondaryRenderer` is overridden but **unreachable in this build, for two independent reasons**, and the second is a consequence of combining the features. `buildSecondaryVideoRenderer` returns null unless `enableMediaCodecVideoRendererPrewarming` is set — it is opt-in and `experimentalSetEnableMediaCodecVideoRendererPrewarming` is never called anywhere in this project — *and* unless the primary's class is exactly `MediaCodecVideoRenderer`, compared by class identity rather than `instanceof`. The primary is now `RotationCorrectingVideoRenderer`, a subclass, so that second gate fails even if pre-warming is ever switched on. Unwrapping the primary before delegating therefore no longer preserves pre-warming the way it did before orientation existed; nothing can, and the practical behaviour is unchanged only because pre-warming was already off. The override is kept for shape: `super` is handed the renderer rather than the wrapper, and any secondary it did return gets the same shift, because `RendererHolder` drives primary and secondary from one `rendererPositionUs` and a pre-warm swap into an unshifted secondary would step the picture back by the whole delay.

When the decoder is the mechanism, `KEY_ROTATION` is read once at codec configuration, so a change is only real after the codec is configured again. Applying one therefore re-prepares the **live** player exactly as an in-place subtitle reload does — same instance, same surface, same `MediaSession`, same sideloaded subtitle, same track-selection parameters, resumed at the player's own position with `playWhenReady` restored — and costs a re-buffer and nothing else. Media3 agrees from the other side: `MediaCodecInfo.canReuseCodec` names a rotation change as a discard reason. A rotation change during a subtitle attach's 12-second watchdog window cancels that watchdog, because the rebuilt item carries no attempt tag and the deadline could then only fire against a subtitle that is fine. A re-prepare that fires while a cast is still starting is reported to the cast transaction through the startup callbacks — non-null for exactly as long as the first frame is outstanding, so the condition is structural rather than checked — and buys the one bounded startup-budget grant described under [Receiver validation and playback](#receiver-validation-and-playback).

**A re-prepare is spent only when the decoder still owes the turn** — deliberately not the question "did the commanded number change?", because the two part company in both directions and each mistake costs the viewer the film. A phone re-asserting the choice it already holds is the only way to take a picture back from the TV's own panel, since the phone's selection is optimistic and nothing echoes back, so a plain dedupe on degrees strands a decoder that a re-prepare never reached. The opposite reading is worse: a re-prepare at 4K over Wi-Fi is a re-buffer of seconds whose only visible symptom is a picture that has *not* turned, which is exactly what invites the viewer to press the same key again — and re-issuing on every repeat restarts that re-buffer without bound, each press feeding the next.

`VideoRotationOverride` separates the states by recording a **serial** with each command, and having the decoder's own reading record *which command it consumed* rather than what turn resulted. Three answers are "no re-prepare", and each is a re-buffer not spent: the decoder has consumed this command already; the decoder has read no format at all yet, because the film's first codec configuration is about to carry the commanded value anyway; or a re-prepare for this exact command is already in flight, so every repeat arriving during one stall is absorbed. Only a command that was committed and never carried re-prepares — the repair case, and it is one re-prepare rather than one per press, because the re-issue marks itself as carrying the turn. The serial is also what settles a container declaring a rotation off the quarter-turn grid: `KEY_ROTATION` accepts nothing else, so that file is presented as filed and no command can move it, and recording the consumed command rather than the achieved turn is what stops it demanding a re-prepare forever that provably cannot change the picture. This is what makes the sender's non-deduped `setRotation` free: re-asserting an unchanged choice costs a comparison on the TV and nothing else.

**The path is instrumented end to end**, because nothing on this verb comes back — no ack, no `state` field, no readout — so a turn that fails to arrive has to be diagnosable from the TV's own log in a single install-and-test pass, per command and never per frame:

- `[ws] send drop t=setRotation reason=no_session|oversize|write …` and `[cast] setRotation drop castIdFp=… choice=… degrees=…` — the PHONE's half, and the reason `PlaybackSession` records the optimistic turn only after the frame has reached a live socket. Every verb goes out through the same `ControlClient.send`, so the first line exists for all of them; the second names the turn the first one only names a reason for. Successes are deliberately not logged — a scrub and a walked audio delay each put 20-25 frames a second on this channel — so a `[cast] setRotation castIdFp=…` line is a frame that reached the socket, and its absence under a press is a frame that did not.
- `[ws] command drop cmd=setRotation reason=superseded …` — the frame validated on the Ktor worker, then lost the cast between there and the main thread. Silent to the phone by design; said out loud here so "phone sent, TV did nothing" is not ambiguous with a socket that never delivered.
- `[cast] command drop cmd=setRotation reason=not_current …` — same shape, one layer in: the session no longer owns that `castId`. `setAutoRotation` and `setAudioDelay` say the same thing, and for the same reason — these are the verbs with no echo.
- `[player] rotation choice=Quarter extraDegrees=90 via=frames frameDegrees=90 note=none carried=true decoderExtraDegrees=0` — the receiver's half: what was asked, what it resolved to, which mechanism owns it, what that costs the picture, and whether any work went out or the turn was already there. `carried=false` is the deliberate no-op above, not a failure; `note=NotOnThisTv` is the refusal the panel is also showing.
- `[player] rotationToDecoder container=0 decoder=0 extraDegrees=90 applied=0 via=frames command=3` — the decoder's half, written on the playback thread from a single read of the command, so the pair can never be two different commands spliced together. `command=` is part of the key it de-duplicates on, so every re-prepare's read appears beside the `rotation` line that caused it. `via=frames` is what makes `decoder=0` under a non-zero `extraDegrees=` correct rather than a dropped command — the graph is carrying the whole turn, including the container's own. Under `via=decoder`, a `decoder=` equal to `container=` on a non-zero `extraDegrees=` is the off-grid container, stated rather than left as silence that reads like a media3 failure.
- `[player] turnMechanism via=frames frameDegrees=90 colour=Sdr note=none glOutput=pq=false hlg=false` — written once per mechanism change, at the player swap that performs it. `glOutput=` is this panel's own EGL answer, read from the device, and it is the line that says whether a turn on this TV can keep HDR at all. `[player] turnFrames failed code=…` precedes it when the fallback is what caused the swap.
- `[player] videoSize w=1920 h=1080 par=1.0 decoderExtraDegrees=0 via=frames` — what the renderer thinks the picture's shape is, which is a different claim under the two mechanisms. Under `via=decoder` it is **not** proof the codec obeyed: media3 1.10.1 swaps these dimensions and inverts the sample aspect from `Format.rotationDegrees` on its own assumption that it did, and this TV's display pipeline does not — a box that changed shape over a picture that stayed sideways is exactly the failure that put the frames mechanism here. Under `via=frames` these stay the **coded** dimensions, landscape for a film turned on end, and that is correct rather than a symptom: the graph is registered with the same coded size and fits the turned frame into the surface itself.

The automatic half is `autoRotation` in `player/VideoOrientationPolicy.kt`, pure and unit-tested. The trap it exists for is that a genuine portrait phone recording is stored **exactly** like a mis-tagged landscape film — a 1920×1080 coded frame with a 90° display matrix, because the sensor reads out landscape and the container records how the phone was held. Nothing in the video track separates them, so a rule written on the video track alone would turn every portrait clip in the user's gallery on its side: a rare annoyance traded for a common one. What separates them is everything around the picture. A released title is assembled — more than one audio track, or a surround/broadcast codec no phone records (AC-3, E-AC-3, E-AC-3 JOC, AC-4, TrueHD, DTS and its variants) or a channel count of six or more, or subtitle tracks the container itself declares — while a camera clip carries one stereo AAC track and nothing else. The correction fires only on positive evidence of assembly, above a 10-minute duration floor, on a coded frame that is landscape (sample aspect included, so 1440×1080 at 4:3 counts) with a container rotation of exactly 90 or 270. Everything else honours the container, and the default when the rule does not fire is byte-identical to the previous behaviour. Coded aspect ratio wider than 16:9 and cinema frame rates are deliberately **not** used as evidence: some phones record 21:9, and 24 fps is an option on the phones whose clips this must not touch. A film whose coded frame is portrait with no rotation at all is not detectable as an error and is left to the manual override.

`Tracks` is the earliest place that evidence exists — the audio and text tracks are invisible to a video renderer — so the verdict is read on the main thread in `onTracksChanged`, where it arrives before the first frame: the playback thread publishes the selection in an earlier pass than the one that can produce a decoded frame, and both reach the main thread through the same Looper queue. A verdict that landed late would cost a re-buffer rather than a wrong answer. A sideloaded subtitle is subtracted from the text-track count, because a `.srt` the viewer picked on their phone says nothing about how the film was authored. The verdict and its reason are logged (`autoRotation extraDegrees=270 verdict=LandscapeFilmFiledSideways`).

The manual half is the transport's own **orientation tile** and the panel it opens: `AUTO`, `0°`, `90°`, `180°`, `270°`, in the same cell vocabulary as the caption sizes. The tile is a square whose whole content is the turn currently on screen, because here the state IS the name — five values, none longer than four glyphs — so the degrees are the hero and a glyph beside them would have nothing to add. It sits beside the subtitles card, which gave up the track name it used to state to make room; that card now says only `SUBS` and `ON`/`OFF`, and the panel behind it is the only surface with room for a track name anyway. The degrees are the turn Flick adds **on top of** the container's own, which is the only reading under which every presentation is reachable — a file tagged 90 and a file tagged 0 need different absolute answers to look the same, and the viewer looking at a sideways film knows only what they can see. `0°` is therefore the row that means "honour the file exactly", and it is what corrects an Auto that read the file wrong. While Auto is chosen the section's eyebrow states what it decided (`AUTO · 90°`); every other choice already says so by being the selected cell. The choice is owned by `PlayerController`, survives a background/foreground cycle with the player, and resets to Auto for every new cast.

The control protocol carries the same choice from the phone under a `setRotation` verb with **two** accepted shapes, validated in `net/RotationCommand.kt` and dispatched under the same cast-ownership rules as `setVolume`:

- `{"t":"setRotation","v":2,"castId":"<id>","degrees":<0|90|180|270>}` — the phone **asserting** an orientation. Quarter turns only, because `MediaFormat.KEY_ROTATION` accepts nothing else, so a value off that grid is a malformed frame rather than one to snap.
- `{"t":"setRotation","v":2,"castId":"<id>","auto":true}` — the phone giving the reading **back**. It lands on `setAutoVideoRotation()`, which selects `VideoRotation.Auto` and therefore re-applies `autoVideoRotationDegrees` — the verdict `onTracksChanged` holds for the film that is playing, not the degrees Auto resolved to when it loaded.

Two `o.exactly(...)` field sets, never a permissive check — the construction `denied` uses for its 2-key and 3-key forms and `loadFailed`/`error` for their with- and without-`httpStatus` forms. Auto is deliberately **not** a sentinel inside `degrees`: a mode living in the value domain of a numeric field is what would stop a value off the quarter-turn grid from being malformed on sight. `auto` accepts only `true`, because there is no "not auto" to command — the other shape carries the degrees. Without the second shape the control would be one-way: a viewer who rotated once could never hand the decision back. `ControlProtocolV2.capabilities` is deliberately **unchanged** — capabilities are compared for exact equality, so widening them would force every paired phone to re-pair, and a frame the peer refuses is a per-command failure rather than a pairing one.

On the phone the same five choices are reached by **one key on the Now Playing poster**, not by a row of cells. It is a square wearing the turn currently in force, in the corner of the still it turns, and each press advances a quarter — `Auto → 90° → 180° → 270° → 0° → Auto`. The walk deliberately does not follow `VideoRotation.ALL`'s order, which opens on 0°: a control that only moves forwards has to spend every press on a turn, and on the very film the key exists for — the sideways one whose container declares nothing, which Auto therefore reads as 0° — a first press asserting 0° would change no degrees and the picture would stand still. The circle closes on Auto because Auto is the receiver reading the file for itself, and a forward-only control must be able to hand that reading back.

The sheet's five cells were where this used to live. A single key replaced them because the two surfaces were the same control twice, and because a stepper states the current turn in the place the viewer is already looking rather than in a sheet they have to raise. The key is dimmed rather than hidden unless `castCommandable` holds — an **Active** cast on a **CONNECTED** socket, the same guard that arms the media notification's transport — since a control that vanishes mid-film is a worse answer than one that says it cannot act. It is not deduped against the held selection: that selection is optimistic, no frame carries the TV's own reading back, and re-asserting is how a viewer takes the picture back from a panel that moved it.

The control is signed now, but it is still not on screen: the chrome auto-hides four seconds into a film, which is about when a viewer decides the picture is wrong. So the TV — the only side that knows the picture turned, or that it is presenting a tall strip on a landscape panel, since no frame carries that reading to the phone — says so once per cast, over the film, for `ORIENTATION_HINT_MS` (6 s). It leads with the transport's orientation tile **in miniature** — the same square, the same unfocused control fill and hairline, the same degrees — because that is the thing it is sending the viewer to look for, and it names the control by what it wears rather than by the name of a panel. It is a silhouette and not a copy: the hint only ever shows while the choice is Auto, so the real tile carries an `AUTO` eyebrow over those degrees that the 38 dp square has no room for, and the degrees are what the line beside it names anyway: *"Turned this film upright / CHANGE IT ON THE 90° TILE"* and *"Showing this film as filed / TURN IT ON THE 0° TILE"*. The degrees in the sign and the degrees on the tile are one resolved value passed to both, so they cannot disagree. It is a drawn silhouette rather than the control itself: this is a sign, and a sign that could be pressed would be a second control appearing over the film.

The decision is `player/OrientationHintPolicy.kt`, pure and unit-tested; the screen renders it and decides nothing. It fires for exactly two readings, both of them cases where the viewer might want the control and cannot currently find it: **Auto corrected the film** (the picture is right, but they were shown something other than what the file asked for, and are owed the way back), and **the presented picture is portrait and Flick did not correct it** — which covers a mis-tagged film the evidence rule was too conservative to touch *and* a genuine portrait recording, the two the video track cannot separate. The presented shape is derived from the container by `presentedShape` rather than read back off a decoded frame, because the only reason to ask is to say something at the start of a film, and because the reported `VideoSize` no longer answers it under both mechanisms — the effects graph deliberately leaves it at the coded size. `presentedShape` is pure geometry over the container's turn plus Flick's, so it states what the viewer is looking at whichever mechanism produced it, one step sooner than any frame; a turn off the quarter-turn grid is "say nothing". A rotation the viewer chose themselves never fires it — `VideoRotation.Auto` is the gate, and it is the honest one, because an explicit choice is the only way the picture moves without Flick having decided anything. Someone holding the control does not need to be told where it is.

Three placement rules, two of them from the hardware. It is **not** a centred state chip: the middle of the frame carries FINISHED alone, and this is a pointer to a control rather than a state. It stays out of the bottom third entirely, where the transport panel, the resting pause key and media3's `SubtitleView` all land. That leaves the band under the top pill row, centred, which clears END SESSION on the left and the clock on the right in every chrome state — and it does not move when the chrome falls away at 4 s, which is what says it is not chrome. It **waits out the T8 quality flourish**: that card's rows are `fillMaxWidth`, so on the real panel it is full-bleed across the same band and the first capture had the two drawn one on top of the other. Waiting is also the better read — two transient cards at once is two things talking, and a viewer 4.5 s into a sideways film has had time to wonder what to do about it. An **open side panel spends it rather than hiding it**: a viewer with any panel open has the chrome up and the tile in front of them, so they no longer need the sign, and 200 dp to 488 dp of panel glass reaches up through the frame it would otherwise sit on. It is never focusable, never clickable and never in the accessibility graph as a control, so the chrome's own 4 s countdown, `TvRemoteKeyPolicy` and the panels' focus vetoes all see exactly what they saw before; enter and exit are the flourish's own `fadeIn`/`scaleIn` + `fadeOut`/`scaleOut`, which are `graphicsLayer` properties, so nothing over the decoder is re-laid-out while it moves. The reading is published from `onTracksChanged` beside the verdict — the case it exists for is the one the correction does *not* act on, so it cannot ride on a change of degrees — logged as `orientationHint=ShownAsFiled verdict=LooksLikeACameraClip`, and cleared with the rest of the rotation state, so it never survives a cast ending or a re-target. The phone is unchanged and no frame grows a field: the hint is the TV stating its own reading of the file, which is the one thing the wire deliberately does not carry.

The phone's selection is **optimistic**. It is seeded to Auto by `loadMedia`, which is the same reset the receiver performs per cast, so the two genuinely agree at the start of every film; a press records the choice and sends the verb, exactly as a local play/pause holds its commanded value. Nothing echoes it back, and deliberately so: the `state` frame is validated against an exact field set on *both* sides, so a rotation field added to it would be rejected by every phone or TV not updated in lockstep — the entire playback UI traded for one readout. The consequence is stated rather than papered over: **if the viewer also uses the TV's own panel mid-cast, the phone's displayed selection can disagree with what the TV is applying until the next cast reseeds both.** The phone therefore shows no `AUTO · 90°` readout — that verdict is the receiver's reading of the file and no frame carries it, so the phone states the choice it made and claims nothing about the answer.

## Lifecycle and structured failure

Control connection, cast ID, and receiver cast generation guard every queued mutation. A new cast supersedes the old generation; stale callbacks/commands cannot mutate the new player. A WebSocket close calls the lease-guarded `onControlLost(generation)`, so a displaced/stale socket cannot tear down its successor. Activity background, LAN loss/change, and endpoint rebind use `forceLocalTeardown()` before server teardown because those local-authority events must clear the current cast regardless of socket lease. While preparing/active, a resumed phone receives proof-bearing `resumed` then `busy(active_cast)`; a newly paired phone receives `paired` then `busy`, preserving the key through the internal `PairedBusy` result. Neither can displace the owner.

`stop(castId)` is the canonical terminal command for the current Checking/Preparing or Active cast. The receiver clears player/session ownership, sends cast-correlated `stopped`, and replays that retained result for a duplicate stop. The sender reducer treats matching `stopped` as terminal, runs cast-correlated foreground-service cleanup, and returns to Library; local cleanup never waits indefinitely for the acknowledgement. `cancelLoad` remains the sender's best-effort pre-ready cancellation path; local TV Back uses the same stopped terminal path rather than silently clearing an active cast.

TV background, LAN loss/change, control stop/loss, cancellation, and terminal failure invalidate the session before stopping/clearing media items, URL, title, startup callback, retry state, and decoder ownership. While backgrounded the TV stays bound and advertised as `state=sleeping`, and `ReceiverBindingGate` refuses `loadMedia`; the socket accepts no new cast. Foreground return requires a fresh authenticated cast; v2 has no background playback resume.

### Control-socket transport failures

Ktor runs the WebSocket ping/pong watchdog as a coroutine of the session, not of the code that opened it. On timeout it does not merely close the socket: it closes the session's `incoming` channel **with** `IOException("Ping timeout")` as the channel's cause, so the phone's authenticated reader loop receives a throw rather than an end of iteration. That reader is a plain `applicationScope.launch`, and `SupervisorJob()` stops a child's failure from reaching its siblings but not from reaching the thread's default uncaught handler — so with no `CoroutineExceptionHandler` anywhere in that context the process died and the user was dropped to the launcher mid-film. `ControlClient.open`'s try/catch could never catch it: the watchdog is a sibling of the `action(socket)` call and had long since returned.

The reader now runs its loop inside `absorbingTransportFailure`, which classifies anything that escapes through the pure `ControlTransportFailure` and takes its logging and teardown as parameters so the disposition — not just the predicate — is exercised by a JVM test against a channel closed exactly the way the watchdog closes it. The reader also carries a `CoroutineExceptionHandler` **on its own `launch`** as the backstop for anything that escapes the shell itself — a handler is consulted only on the context of the coroutine whose failure reaches a root, and under a supervisor that root is the reader itself, so a handler installed on any scope that did not launch it would never run. `FlickApplication.applicationScope` deliberately stays handler-free: it also carries the library load, the subtitle job, frame collection and every pairing job, and a blanket handler there would hide genuine defects in all of them.

Classification is an allow-list of what the control socket's coroutines can actually observe — `IOException` and its subtypes, the closed-channel exceptions, `FrameTooBigException`, `ProtocolViolationException` — matched on the throwable itself and never through its cause chain or through a supertype: `ClosedSendChannelException` *is* an `IllegalStateException` and `ClosedReceiveChannelException` *is* a `NoSuchElementException`, so a supertype rule would swallow ordinary defects. Cancellation is re-raised so `reader?.cancel()` keeps meaning something, and everything else — including every `Error` — is re-raised unchanged and still crashes. An absorbed failure lands on `ConnectionStatus.DISCONNECTED` through the same identity-guarded teardown a close uses (`session === socket`, so a late failure from a prior socket cannot tear down its successor), which the reducer already reports as `control_disconnected`. The dial-time taxonomy is untouched: a transport failure after authentication is not an `Unreachable`/`TimedOut`/`RejectedByTv`/`ProtocolError` dial result.

The ping interval is 15 s, and it buys two different numbers that must not be confused. Ktor derives the pong deadline as exactly twice the interval and offers no separate setting, and its pinger spends a whole interval draining stale pongs *before* it puts the next ping on the wire: a stalled link is therefore tolerated for **2× = 30 s** of missing pong once a ping is out, while a TV that dies is noticed only **between 2× and 3×, i.e. 30–45 s** later — the phone reads CONNECTED over a dead cast for that whole window, so a hardware check of a pulled-power TV should expect the Failure route at up to 45 s, not 30. The tolerance floor is what the value is chosen for: the previous 5 s tolerated 10 seconds, which an ordinary home-Wi-Fi stall under a 4K VBR peak exceeds, and past that point the receiver's lease is released and the cast is gone; the 45-second detection ceiling is the price. 15 s also keeps a ping on the wire about every 15 seconds, inside Ktor CIO's 45-second server connection-idle timeout, so an authenticated but idle session is never reaped for silence. The receiver is unaffected in both directions: the server WebSockets plugin's `pingPeriod` defaults to zero and `ControlServer` never sets it, so the TV installs no pinger and cannot raise this failure at all, and the pong is answered by Ktor's own ponger rather than by `ControlServer`, so single-controller ownership never sees it. The TV is structurally protected as well — Ktor's `WebSocketUpgrade` runs the handler inside a `catch (Throwable)` that converts any escape into a scope cancellation, so a throw out of the receiver's read loop still runs its lease-releasing `finally` and can never reach an uncaught handler.

Wire failures are stable lowercase codes with required `retryable` and optional HTTP status only when observed. Raw exception text is never serialized. Classification is evidence-conservative: actual parser/decoder/network/status evidence is used, while ambiguous codec/HDR failures stay broad (`unsupported_video_format`, `decoder_init`, or `unknown`). Phone-local pre-control/source/bind failures remain phone-only; adopted receiver failure reaches both devices only while control is still usable.

## Privacy and diagnostics

Pairing preferences are excluded from legacy backup, cloud backup, and device transfer. The notification names the video the user is casting and the TV they are casting it to — it is a media notification and both are the point of it — and still omits URL, token, and private address. Diagnostics may show redacted probe/startup time, HTTP status, Wi-Fi band/link speed/RSSI, decoder, resolution/HDR class, and buffer/rebuffer/drop/recovery counters; export/log/committed evidence must not include pairing material, full URL/token, raw private address, SSID/BSSID, serial, or title.

### Runtime logging

Both modules ship one small logger with an identical shape: `FlickLog` in `receiver/util` under tag **`FlickTV`**, and `FlickLog` in `sender/util` under tag **`FlickPhone`**. Line format is `[area] key=value key=value`.

The shared core `area` vocabulary is `bind`, `lan`, `nsd`, `ws`, `auth`, `pair`, `cast`, `probe`, `player`, and `http`; the receiver additionally uses `subtitle` for selection-only MIME diagnostics.

`v`/`d` are gated on `BuildConfig.DEBUG` (both modules set `buildFeatures { buildConfig = true }`; AGP 8 defaults it to false and generates no class at all). `i`/`w`/`e` always emit. Every level appends to a 200-entry in-memory ring buffer exposed as a `StateFlow`, which is never persisted to disk or backed up. Helpers: `fp(value)` returns an 8-hex SHA-256 prefix; `endpoint(url)` returns `scheme://host:port` only, because the path is the media token.

**Redaction contract.** Safe at any level: bound host/port, peer IP, NSD name/model/state/version, `tvId`, `keyId`, device labels, enum and sealed-class simple names, wire result codes, HTTP status, counts/lengths/attempts/generations, latencies, decoder name, resolution, HDR type, selected subtitle MIME/cue shape, Wi-Fi band/RSSI. Never, at any level: the four-digit pairing code, the pairing `key`, the HMAC `proof`, the media session token, any full `/v/{token}` URL, the raw deep-link URI, subtitle cue text/bitmap payload, SSID/BSSID.

**Do not fingerprint the pairing code.** A SHA-256 of four digits has a 10,000-entry rainbow table, so a hash pasted into a bug report *is* the plaintext code. Log `codeLen=4` / `codePresent=true` instead. Nonces may be fingerprinted but never printed verbatim. There is deliberately no generic `log(frame)` helper — per-field call sites are what keeps secrets out.

Log message bodies are English literals in code. This is developer output, not user-facing copy, and is a recorded exception to the strings.xml rule; the diagnostics UI chrome around them is still a string resource.

Every pre-auth rejection names itself locally (`not_bound`, `port_unbound`, `host_pin`, `peer_not_private`, `preauth_limit`, `auth_timeout_or_denied`), and every lifecycle edge that touches the binding carries a named trigger (`on_start`, `on_stop`, `no_lan_address`, `addr_changed`, `dispose`). The wire bytes are unchanged: reasons are logged locally only.

**Capture recipe.**

```sh
# TV
adb connect <tv-lan-ip>:5555
adb logcat -c && adb logcat -s FlickTV:V

# Phone
adb logcat -s FlickPhone:V
```

`adb logcat` is unusable on some OEM builds, so both apps also render their ring buffer in-app: TV **Settings › Diagnostics**, phone **Diagnostics › Copy**.

## Release and rollback

Sender and receiver 0.2.1 must ship together. A v2 sender neither authenticates unversioned control nor falls back to optimistic v1 playback. Rollback installs a matched prior implementation on both devices using a newly higher `versionCode`; uninstall/reinstall clears pairing data. Host/token validation, explicit LAN binding, generic auth denial, no-redirect playback, and hardware-only decoding are not independently rolled back.
